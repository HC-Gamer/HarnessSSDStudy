Week 2 实验心得

一、Hooks：把"我记得要检查"变成"系统不会忘"

写 hook 之前，我对质量的保障方式是"我自己看一眼"。这套办法在数据量是 3 条的时候完美运行，到 30 条就已经开始糊弄自己了。Hooks 真正解决的不是校验这件事本身——校验逻辑我随手就能写在主流程里——它解决的是"标准的存放位置"问题：质量标准从我的记忆里，搬到了系统的执行路径上。这中间的差别是，前者会疲劳、会侥幸、会在赶时间的时候被跳过，后者不会。

踩的第一个坑是，我最初把格式校验和质量评分写在同一个 hook 里，一起返回通过/不通过。跑了一轮才意识到这两件事的语义根本不同：JSON 格式错误是硬失败，脏数据进了库下游全崩，必须阻断；质量分低是软信号，它只是在说"这条可能不太行"，不该拦住流水线。混在一起的后果只有两种，要么我把阈值调松，垃圾照样进库，要么调紧，天天被误报轰炸，最后的结局一定是我把 hook 关掉。所以我把它们拆成了两个文件。这条经验我觉得可以推广：任何自动化闸门，第一步都得先想清楚它是 block 还是 warn，想不清楚就别装。

第二个更让我不舒服的发现是，均分 80.4、25 篇 A 级，这个数字很好看，但 Lobsters 那批只有二三十字的摘要也拿到了 B。也就是说，我的评分规则在给一批对下游几乎没有使用价值的条目发合格证。问题不在 hook，在我：设计评分维度的时候，我其实是在给"我希望数据长什么样"打分，而不是给"这条数据对检索和阅读有没有用"打分。Hook 会忠实、稳定、不知疲倦地执行我写下的标准，包括我写错的那一部分。它放大的是我的判断力，不是替代我的判断力。这个认识让我对"加 hook 就变可靠了"这种说法警惕了很多。

二、MCP：外部连接的本质是让数据变成"可被提问的东西"

MCP server 我写了三个 tool，技术上并不难，stdio 收发 JSON-RPC 而已。但做完之后回头看，最难的部分完全出乎我的意料——是 tool 的描述文字。

因为 tool description 不是给人看的文档，它是给模型看的 prompt。参数叫 `q` 还是 `query`、描述里有没有写清"最多返回 N 条"、要不要说明标签是精确匹配还是模糊匹配，直接决定了模型会不会用错这个工具。我在这上面改了好几轮，本质上是在做一件我以前没做过的事：为一个"会认真读文档但也会自由发挥的调用方"设计 API。传统 API 的调用方是程序，写错了就报错；MCP 的调用方是模型，写得含糊它不会报错，它会猜，然后给你一个看起来很合理的错误结果。这是一种全新的失败模式。

调试上的坑很典型：任何一个 print 到 stdout 的调试语句都会污染协议，server 直接挂掉。逼着我把所有日志改到 stderr。表面看是个技术细节，往深了想是个原则——通道必须单一职责，数据通道里不能掺人看的东西。

但最大的收获是认知层面的。我原本以为 MCP 是"给 AI 加功能"，做完才明白它其实是"给数据加接口"。knowledge/articles/ 里那堆 JSON，在有 MCP 之前只是我这条流水线的私有产物，脚本跑完就躺在那儿；套上 MCP 之后，它成了任何一个 agent 会话都能查询的公共资产。价值不在那几百行 server 代码，在于它把一次性的脚本输出，变成了可以长期复用的基础设施。这是我这周对"外部连接"这个词理解最深的一次。

三、CI/CD：从"我跑一次"到"它一直在跑"

把采集挂上定时任务之后，我意识到一件挺反直觉的事：自动化把系统的失败模式，从"报错"变成了"沉默"。

我本地跑，5/7 成功，看着挺不错，失败的两个源我当场就看到了。可一旦进了 daily-collect.yml，Hugging Face 那个 403、arXiv 那个超时，就变成了每天在没人看的日志里安静地发生一次。它可以连续静默失败一个月，而我坐在这里以为知识库在稳定增长。真正的风险从来不是 71% 这个成功率，是我不知道它是 71%。

所以我给自己定的下一步不是"把成功率提到 100%"，而是让这个数字本身可见、可追踪、变化的时候能叫醒我。自动化的第一性问题不是"能不能跑起来"，是"跑挂了我怎么知道"。

顺带暴露的另一个问题是幂等性。定时任务的本质是会重复执行，而我的 ID 用的是日期加序号，同一天重跑会怎么样？覆盖还是产生重复条目？我现在还没完全处理干净，先记在这里。手动执行的脚本可以不考虑重入，定时执行的不行——这是两种不同的东西，我之前把它们当成了同一个。

还有一层是角色的变化。定时触发之后，我不再是流程里的一环了，我从操作者变成了设计者和值班人。这个转变听起来轻描淡写，实际上意味着我要开始关心的东西完全变了：不再是"这次跑得对不对"，而是"它长期跑下去会怎么退化"。

四、成本控制：¥0.0014 教会我的根本不是省钱

3 次调用，1109 tokens，一分四厘，月估两毛五。这个数字小到近乎荒诞，所以 CostTracker 的意义显然不可能是省这两毛五。

它的意义是，在成本还完全不构成压力的时候，就先把度量装上。因为成本数字真正的作用是充当架构决策的信号——当我看到平均每条 370 tokens，我立刻就能推算出每天一千条是什么量级，能判断"要不要给每条做 embedding"、"要不要换更贵的模型做深度分析"这类决策的边界在哪里。没有度量，这些判断只能靠感觉，而感觉在数量级面前一向不太可靠。度量的价值从来不在它报出的那个数，在于它让原本要拍脑袋的决定变成了可以算的账。

但这周成本这一块最贵的教训在另一边。技术深度评分整体偏低，规则降级 5/10，LLM 也只有 6/10。我第一反应是怀疑模型能力不够，想着是不是该换个更强的。查了之后发现根本不是模型的问题：RSS 源只给了标题和一句话摘要，输入端就没有深度，模型再强也变不出来。差点为一个输入问题去支付一笔模型升级的费用——这才是最典型的成本陷阱。成本优化的第一步永远不是换便宜模型，而是别把钱花在垃圾输入上；而 garbage in 真正的代价，也不是结果差，是它会误导你以为需要花更多钱去修模型。

标签同质化那件事同理。Hacker News 和 OpenAI Blog 的条目全被标成 "llm"，这不是模型偷懒，是我的 prompt 里根本没给出标签体系的约束。我为了省 token 写了个很短的 prompt，省下来的那点钱直接换成了低质量输出。在这里，成本和质量根本不是需要权衡的两端，它们是同一个设计问题的两面。

五、总反思：Harness 到底是什么

做完这四块，我越来越觉得 Harness 不是一堆工具的集合，它是把"意图"翻译成"系统行为"的那一层结构。

回头看，这四个维度其实是在回答同一个问题的四个侧面：这件事什么时候发生（CI/CD 管时间触发，Hooks 管事件触发）、它能碰到什么（MCP 定义边界与连接）、它消耗什么（成本度量）。合起来，就是给一个本质上非确定性的智能体，划出一个确定性的运行空间。

LLM 是概率的、会飘的、无状态的、每次都从零开始。而 Harness 提供的恰好全是它没有的东西：确定的触发时机、确定的校验闸门、确定的外部接口、确定的资源账本。智能在中间，可靠性在四周。这大概就是为什么模型能力年年翻倍，工程脚手架的活却一点没少——那些活从来就不是模型能干的活。

但我这周体会最深的一句话是这个：Harness 里我写下的每一条规则，都是我的判断的固化。hook 的评分权重、prompt 里的标签约束、cron 的频率、timeout 的秒数——这些看起来都是"配置"，实际上是我对"什么算好"的定义被写进了系统。而系统会诚实地、不知疲倦地执行它，包括执行我判断错的那部分，并且以远超我手动操作的规模执行。

所以搭 Harness 真正在训练的，不是工程能力，是把模糊的品味变成可执行标准的能力。自动化并没有让我从思考里解脱出来，它只是把我的思考大幅提前了，然后放大了后果。
