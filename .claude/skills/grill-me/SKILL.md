# grill-me —— Spec 逐条拷问技能（Claude Code 版）

与 [`.opencode/skills/grill-me/SKILL.md`](../../../.opencode/skills/grill-me/SKILL.md) 同源，
逻辑一致，工具与输出方式适配 Claude Code。**两份文件的判据表和四类问题必须保持同步**。

---

## 为什么需要它

SDD 假设「spec 是唯一事实来源」。这个假设只在 spec **没有歧义**时成立。
而歧义不会自己暴露——它会在 Agent 按字面执行、产出跑偏之后才暴露，那时钱已经花了。

本技能把暴露过程提前到写代码之前：让 Claude 扮演一个刻薄的评审，逐条反问。

## 硬约束

1. **只读**。本技能只用 Read / Grep / Glob。
   **绝对不允许**调用 Edit / Write / NotebookEdit 去「顺手改好」——
   一旦替使用者把答案写进 spec，这个技能的全部价值就没了。
2. **不替对方回答**。可以说明「答不上来意味着要补什么」，但不能给出补法。
3. **逐条锚定行号**。Read 返回带行号，输出里一律写成 `specs/coding-standards.md:143`
   这种可点击格式。
4. **不评论文风**。只攻击可执行性。唯一判据：
   **两个不同的人（或 Agent）读了这条，会不会做出不一样的东西？**

## 执行步骤

### 第 1 步：定位并读入

用户指定了文件就读它。没指定时用 Glob 找候选，按此优先级取第一个存在的：

```
specs/coding-standards.md → specs/agents-prd.md → specs/project-vision.md
→ specs/issues/*.md → AGENTS.md
```

候选超过一个时**先问用户拷问哪份**，不要默认全拷。

### 第 2 步：核实 spec 的自我声明（Claude Code 特有，务必做）

spec 里凡是提到具体路径、命令、常量名、字段名的，都用 Grep / Glob 核实一遍。
**这一步能查出的 ⚫️ 已失效条款，往往比通读一遍查出的还多。**

```
Glob:  spec 声称存在的目录/文件（pyproject.toml、tests/、.env.example …）
Grep:  spec 声称的常量名与函数名（QUALITY_THRESHOLD、_self_test、SCORING_SAMPLES …）
```

对照结果直接决定分类：**声称存在但 Glob 查无此物 → 直接 ⚫️**。

### 第 3 步：切分成可追问单元

一条 = 一个可以独立判定「做到了 / 没做到」的断言。
表格的一行、清单的一项、`Acceptance Criteria` 的一个 checkbox 都算。
标题、过渡句、示例代码不算。

### 第 4 步：分类

| 分类 | 判据 | 处理 |
|------|------|------|
| 🟢 可执行 | 有明确主语、动词、阈值、验证方式 | 跳过 |
| 🟡 有歧义 | 两个人可能理解成两件事 | 追问 |
| 🔴 不可验证 | 没有任何办法判定是否做到 | 重点追问 |
| ⚫️ 已失效 | 与仓库现状矛盾（第 2 步查出来的） | 必须追问 |

### 第 5 步：每条选一个最狠的角度

- **语义**——「『尽量』是多少？」「『关键纯函数』谁来定义关键？」
- **动机**——「为什么是 100 不是 88？换成 88 会坏掉什么？」
- **边缘**——「生成的代码超过 100 列且不能换行时怎么办？」
- **冲突**——「这条说 X，第 N 行说 not X，哪条赢？」

三个温和的问题不如一个答不上来的问题。**每条只留一个。**

### 第 6 步：输出到对话（不落盘）

```markdown
## Grill 报告：<文件路径>
> 可追问单元 N 条 · 🟢 a · 🟡 b · 🔴 c · ⚫️ d
> 核实：Glob/Grep 查了 M 项声明，其中 K 项对不上

### ⚫️ <条款原文摘录>  (specs/xxx.md:143)
**问**：<一个问题，不超过两句>
**为什么问**：<不明确会导致什么具体的执行分歧>
**答不上来说明**：<需要在 spec 里补什么>
```

排序 ⚫️ → 🔴 → 🟡，最多 10 条。**收尾是一句反问，不是结论。**

使用者要求把报告存档时才写文件，路径 `specs/grill/<被拷问文件名>-<YYYY-MM-DD>.md`。

## 质量自查清单

- [ ] 每个问题锚定了 `file:line`
- [ ] 第 2 步的 Grep/Glob 核实真的跑了，并在报告头写了核实数量
- [ ] 没有「建议补充」「可以考虑」这类软化措辞
- [ ] 没有替使用者回答任何一个问题
- [ ] 没有调用 Edit / Write
- [ ] 至少有一条 ⚫️ 或 🔴（全 🟢 说明没读进去）

## 反面示例

❌ 「整体规范比较完善，建议在测试章节补充集成测试的具体做法。」
　　—— 没有行号、没有问题、替对方下了结论。

✅ 「`specs/coding-standards.md:397` 写着覆盖率 ≥ 80%，`:583` 又写着『tests/ 不存在，
　　只有模块内 _self_test()』。那今天提交代码的人到底能不能过这条？
　　如果不能过，为什么它写在『规范』而不是『路线图』里？」
