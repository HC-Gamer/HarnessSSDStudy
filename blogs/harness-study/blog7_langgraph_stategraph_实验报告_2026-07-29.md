# 我给管线加了条件路由和反馈循环，然后三次都走了直路 (2026-07-29)

> 用 LangGraph StateGraph 重写线性 sub-agent 管线的实验记录。9 次调用，5,645 tokens，¥0.0091，全部实验质量分 100/100、零重写。
> 以及为什么这三个漂亮数字，其实是一份失败报告。

## 起点：线性管线的天花板

Week 2 我做的是一条三段式 sub-agent 管线：

```
collector ──► analyzer ──► organizer
```

三个 Agent 各有独立的权限矩阵，靠文件系统传递中间产物——collector 写 `knowledge/raw/*.json`，analyzer 读它、把结果吐到 stdout，organizer 接过来写 `knowledge/articles/*.json`。

跑起来是稳的。但它有两个我一直绕不开的限制：

**一是没有运行时分支。** 管线是 must-pass 的，跑到底就结束。analyzer 产出的摘要好还是烂，organizer 一视同仁地归档。

**二是没有回头路。** 我发现质量不行，唯一的办法是人工重跑整条管线。检测在我脑子里，决策在我手上，修复靠我敲命令。

这两件事本质是同一件：**管线里没有"判断"的位置**。所以 Week 3 我把同一条流水线用 LangGraph 的 StateGraph 重写了一遍，想验证四件事——共享状态能不能替代文件传递、运行时能不能条件分支、质量不达标能不能自动回炉、这套东西要多少钱。

## 两种架构

### 线性：文件系统是唯一通道

```
  ┌───────────┐  knowledge/raw/  ┌──────────┐   stdout   ┌───────────┐
  │ collector │ ───── *.json ──► │ analyzer │ ── JSON ─► │ organizer │
  └───────────┘                  └──────────┘            └───────────┘
   WebFetch ✅                    WebFetch ✅              Write ✅
   Write   ❌                     Write   ❌              WebFetch ❌

  单向 · 无分支 · 无回路
  状态外化在磁盘上，进程只是路过它的临时工
```

### 图：共享状态 + 条件边 + 回边

```
                ┌────────────────────────────────────────┐
                │       PipelineState (TypedDict)        │
                │  topic / raw_content / sources         │
                │  summary / key_points / quality_score  │
                │  article_title / article_body          │
                │  rewrite_count / should_rewrite        │
                └────────────────────────────────────────┘
                    ▲       ▲        ▲       ▲       ▲
                    │       │        │       │       │  ← 五个节点读写同一份 dict
   START            │       │        │       │       │
     │              │       │        │       │       │
     ▼              │       │        │       │       │
  ┌────────┐        │       │        │       │       │
  │ search │────────┘       │        │       │       │
  └────────┘                │        │       │       │
     │                      │        │       │       │
     ▼                      │        │       │       │
  ┌─────────┐ ◄──────────┐  │        │       │       │
  │ analyze │────────────┼──┘        │       │       │
  └─────────┘            │           │       │       │
     │                   │ 反馈循环   │       │       │
     ▼                   │           │       │       │
  ┌───────────────┐      │           │       │       │
  │ quality_check │──────┼───────────┘       │       │
  └───────────────┘      │                   │       │
     │  decide_route()   │                   │       │
     │  (conditional)    │                   │       │
     ├─ score < 60 ──► ┌─────────┐ ──────────┘       │
     │  & rewrite<3    │ rewrite │                   │
     │                 └─────────┘                   │
     └─ score ≥ 60 ──► ┌──────────┐ ─────────────────┘
                       │ organize │
                       └──────────┘
                            │
                            ▼
                           END
```

代码上，这个图只有几行声明：

```python
builder.add_edge(START, "search")
builder.add_edge("search", "analyze")
builder.add_edge("analyze", "quality_check")

builder.add_conditional_edges(
    "quality_check", decide_route,
    {"rewrite": "rewrite", "organize": "organize"},
)
builder.add_edge("rewrite", "analyze")   # 回边
builder.add_edge("organize", END)
```

节点函数则退化成最纯粹的形态——收 state，返回 partial dict，由框架合并：

```python
def analyze_node(state: PipelineState) -> dict[str, Any]:
    result = quick_chat(prompt, system=...)
    return {"summary": ..., "key_points": ..., "quality_score": ..., ...}
```

## 结果：三个漂亮数字

| 实验 | 主题 | 调用 | 质量 | 重写 | 耗时 |
|:---:|------|:---:|:----:|:---:|:---:|
| 1 | StateGraph vs 线性管线架构对比 | 3 | 100/100 | 0 | ~14s |
| 2 | 条件路由与反馈循环设计模式 | 3 | 100/100 | 0 | ~15s |
| 3 | 多 Agent 状态共享机制 | 3 | 100/100 | 0 | ~14s |

成本：**9 次调用，5,645 tokens，¥0.0091 / $0.0013**，平均每次调用 627 token、一厘钱。

按这个数据外推，每天 30 条主题走完整图，月成本 ¥2.7；就算每条都触发一次重写，也就 ¥3.6。

如果我在这里收尾，这会是一篇很顺的实验报告：图编排跑通了，质量全满，成本可以忽略。

但这三个数字里，最刺眼的其实是**零重写**。

## 门槛 60，下限 80

`analyze_node` 里的质量分是这么算的：

```python
quality_score = min(100, max(0, 60 + len(summary) // 5 - (3 - len(key_points)) * 10))
```

把实际产出代进去。prompt 要求"80-120 字摘要 + 5 条要点"，模型也照办了：

```
60 + 120//5 - (3 - 5) * 10  =  60 + 24 + 20  =  104  →  min(100, ·)  →  100
```

哪怕摘要只有 80 字、要点只给 3 条（prompt 的下限），也是 `60 + 16 - 0 = 76`。而门槛是 **60**。

**这道门在结构上就关不上。**

所以「质量分 100/100、零重写」不是质量好的证据，是评分函数没有区分度的证据。我不是通过了考试，是发下来的卷子里没有不及格这个选项。

更难受的是，这和我 Week 2 的教训是同一个形状。上周我发现 Lobsters 那批二三十字的摘要拿到了 B 级，当时的总结是"hook 会忠实执行我写错的标准"。这周我又犯了一次，而且更彻底——上周至少分数还有分布，这周直接恒定满分。**一个恒定输出的度量，信息量是零。**

## 没被走过的分支里，藏着一个 bug

因为 rewrite 分支一次都没进过，里面的问题就一直没暴露。我后来读代码才发现：

```python
def rewrite_node(state):
    # ... 带着反馈重新生成更高质量的分析
    return {
        "summary": new_summary,                        # 改进后的摘要
        "quality_score": state["quality_score"] + 20,  # 加 20 分
        "rewrite_count": state["rewrite_count"] + 1,
    }

builder.add_edge("rewrite", "analyze")   # ← 问题在这
```

回边指向 `analyze`。而 `analyze_node` 是**从 `raw_content` 从头重新分析**的，它压根不读 `summary`。所以 rewrite 辛辛苦苦生成的改进版摘要和那 +20 分，回到 analyze 之后被**完全覆盖**。

真正生效的只有 `rewrite_count += 1`——那个防死循环的计数器。

换句话说，我实现的不是"带反馈的重试"，是**原地重摇三次骰子**。

这两件事叠起来，给了我一个比"要写好评分函数"更根本的教训：

> **没有被触发过的代码路径，等于不存在的代码路径。**

我可以在报告里写"实现了自动重写循环"，图确实画出来了，代码确实编译通过了，`decide_route` 也确实每轮都被调用了——但那条 `rewrite` 边，从头到尾一次都没有被走过。这种"看起来有"比"明确没有"更危险，因为它会让我停止思考质量问题，误以为已经有个机制在替我守着。

## 四个维度，四个等量的退步

跑完之后，我把四个维度的收益和代价排在一起，发现了一个太整齐以至于不像巧合的规律。

### 1. 状态管理：从"外化记忆"到"内化记忆"

我一开始把这理解成工程选择题：内存快、无序列化、有类型 vs 文件慢、要 JSON 往返、没类型。按这个框架共享 state 全面胜出。

但这个框架漏掉了最重要的一维。文件传递有个共享 state 完全不具备的性质：**它天然不可变、可追溯、在进程之外**。V1 跑完，`raw/` 和 `articles/` 里躺着完整的现场，我事后随时能打开看。我没为这个能力写过一行代码，是文件系统白送的。

共享 state 把它收走了。进程一退出 dict 就没了。我得主动 dump、主动加 checkpointer、主动决定存哪些字段。

想到这里才意识到，差别根本不在"传输"层面：

- 文件传递是**外化记忆**——状态活在系统之外，进程只是路过它的临时工
- 共享 state 是**内化记忆**——状态活在进程里，进程死了记忆就死了

一旦这么看，很多事就串起来了。为什么线性管线天然能断点续跑、能只重跑某一步、能让我手改一个中间文件再继续？因为它的状态是外化的，每一步的输入都是磁盘上可寻址、可修改的东西。为什么 StateGraph 需要 checkpointer 这个专门概念？因为它把状态内化了，所以必须再造一个机制把状态外化回去。

**checkpointer 本质上是在用框架特性，重新实现文件系统白送给线性管线的东西。**

（顺带：我这次装了 `MemorySaver`，但一次中断恢复都没试过——名字里那个 Memory 就说明了一切，进程死了它一样什么都不剩。等于装了个没通电的保险丝。）

取舍轴其实是：**共享 state 优化开发时的表达效率，文件传递优化运行时的可观测性**。前者服务于写代码的我，后者服务于半夜被叫起来查问题的我。我这次毫无疑问站在了前者那边——所以我拿到了干净的节点函数，也拿到了一个跑完就消失的黑盒，和一个藏在里面很久才被发现的覆盖 bug。这两件事是同一个选择的两面。

### 2. 条件路由：图的价值不是"灵活"

我原本以为换成 StateGraph 的收获是"更灵活"。跑完觉得这个词是错的。

线性管线也能灵活。V1 那三个 sub-agent，我完全可以在 organizer 前面写个 if，分数低就再调一次 analyzer——十行代码的事。图结构没让我做到任何原本做不到的事。

它真正改变的是**这个 if 存放在哪里**。线性管线里控制流藏在函数调用的嵌套关系中，你得读完整个 main 才知道数据怎么走；StateGraph 里控制流被抽成 `add_edge` / `add_conditional_edges` 的声明列表，节点函数只剩"收 state、返回 dict"。

这个转变的价值在改代码时才显形：我要调路由逻辑，只动 `decide_route` 那五行和边声明，五个节点函数一行不碰；我要改分析逻辑，只动 `analyze_node`，不用担心影响它怎么被调用。**编排和执行解耦**——听着像正确的废话，落到手上很具体：我第一次感觉到"流程"是个可以单独拿出来看、单独改、单独讨论的东西。

代价是**数据流变隐式了**。TypedDict 里十三个字段，任何节点都能读写。`analyze_node` 写 `quality_score` → `quality_check_node` 读它写 `should_rewrite` → `decide_route` 读 `should_rewrite`——这条链是隐式的，图上完全看不见。图画出来的是控制流，藏起来的是数据流。V1 用文件传递时谁读谁写明摆着，边界是物理隔离的；换成共享 dict 之后，边界消失了，得靠自律维持。

我现在越来越怀疑，全局共享 state 在节点多起来之后会变成一个新的全局变量问题——只不过它长得像框架特性，所以没人管它叫全局变量。

### 3. 反馈循环：循环引入了"时间"

线性管线里，任何变量在任何时刻只有一个值。加了回边之后，`summary` 的含义变成"最近一次分析的结果"，历史被覆盖了。

我写 `rewrite_node` 时脑子里想的是"带着反馈重做"，但反馈的载体是什么？是上一版的 summary，而它马上就要被这一版覆盖。我处理这件事的方式是靠 `rewrite_count` 计数——**这其实是在用一个标量，代替本该存在的一段历史**。

上一节那个覆盖 bug，根子就在这个思路上的马虎。图结构不是"线性的超集，用了只赚不亏"：它换来控制流的显式化，代价是数据流的隐式化和时间维度的引入。后两样，线性管线是天然免疫的。

### 4. 成本：便宜到无感之后，把关的动机也没了

全部实验跑完不到一分钱，我根本没打开过账单页面。

我想说的不是"DeepSeek 真便宜"，而是我注意到自己的行为变了：整个过程我一次都没因为成本犹豫过。要不要多加一个 `search_node`？加。要不要给重写留三次机会？留。三个主题都跑？跑。

这些决策在成本高的时候是需要掂量的，现在全退化成了"想加就加"。而我意识到一个副作用：

> **当一个约束消失时，我并不会自动获得对剩下那些约束的敏感度，我只会变得更随意。**

具体到这次：我给重写设上限 3，理由写的是"防死循环"，但我当时脑子里几乎没有过"三次重写要多花多少钱"这个念头。如果 token 很贵，我会被迫去想"这次重写值不值"，从而顺带想清楚"重写到底改进了什么"——而那恰恰是我搞错的地方。

成本压力有一个我以前没意识到的副产品：**它逼你为每一次调用找一个理由**。理由找不出来，调用就不该存在。成本归零之后这个把关动作也一起没了，于是我加了一个自己都没想明白语义的循环节点。

另外值得一提的是：**图编排本身不花钱**。LangGraph 的调度、路由、checkpoint 全在本地跑，Token 成本 100% 来自节点内的业务调用。V3 比 V1 贵约 6 倍，是因为有效 LLM 步骤从 1 个变成 3 个，不是因为用了图。真正的成本风险在循环——最坏情况 `3 + 3×2 = 9` 次调用，是当前的 3 倍。所以 `rewrite_count < 3` 这个 guard 同时是**正确性保护**和**成本熔断**。

## 那条整齐得可疑的规律

把四个维度串起来看：

| 维度 | 拿到了什么 | 失去了什么 |
|------|-----------|-----------|
| 图结构 | 控制流显式化 | 数据流隐式化 |
| 质量门禁 | 检测自动化 | 检测本身没被检测 |
| 低成本 | 实验自由度 | 每次调用的把关动机 |
| 共享状态 | 代码表达效率 | 运行现场 |

**每一项进步都伴随一个等量的退步，而退步的那一半，全都落在"我怎么知道它对不对"这个维度上。**

这个规律整齐到不像巧合。我现在的理解是：Week 2 我搭的是**执行能力**——hooks、MCP、CI/CD，让系统能干更多事。Week 3 我搭的是**编排能力**——让系统能自己决定怎么干。而这两周我都默认了同一件事：能力增强了，可靠性会跟着涨。

这次的结果很清楚地否定了它。能力和可观测性是两条独立的曲线，而且往往此消彼长——因为让系统更能干的那些手段（内存共享、自动路由、循环重试），恰恰都是让运行过程更不透明的手段。

上周我写过一句：Harness 里我写下的每一条规则，都是我的判断的固化。这周补一句：

> **每一条规则也都是一个未经检验的假设，直到它在真实运行中被触发过至少一次。**

## 结论

零重写、满分通过，这两个数字在报告里看起来是成绩，实际上是一份"从未被测试"的证明。

我做出了一个有条件路由和反馈循环的系统，但三轮实验走的是和线性管线**完全相同**的路径——`START → search → analyze → organize → END`，没有分支，没有循环。

我花了一周造了一台能拐弯的车，开了三趟直路，然后在报告里写"转向系统工作正常"。

所以下一步不是把门槛从 60 提到 90（那只是换个数字继续自欺），排期是这样的：

1. **构造一条必然不及格的输入**，逼这台车拐一次弯——先证明闸门能关上，再去调它关的位置
2. **修回边语义**：改成 `rewrite → quality_check` 跳过 analyze，或让 `analyze_node` 感知 `rewrite_count` 走不同 prompt
3. **重做质量分**：换 LLM-as-judge 或复用 Week 2 的五维评分 hook，让分数真的有分布
4. **换持久化 checkpointer**：SQLite/Postgres，把中断续跑和 time-travel 真跑一遍
5. **在节点边界落盘快照**：不为传递，只为留痕——把"外化记忆"补回来

最后一条我想多说一句。它听起来是把两边的开销都担了，但我现在觉得**可观测性的开销从来不该被当成开销**——它是上面那个覆盖 bug 拖了这么久才被发现的直接原因。

九次调用花了不到一分钱，我读代码找那个 bug 花了半小时。真正稀缺的从来不是 token。
