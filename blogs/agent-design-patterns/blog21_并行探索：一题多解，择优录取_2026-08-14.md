# 并行探索：一题多解，择优录取

上周我的 UE5 项目遇到一个编译错误，我同时让 Codex 和 Claude Code 各诊断了一次。两个模型都很快给出了"很有把握"的答案——但结论互相矛盾：一个说是头文件循环引用，一个说是 LiveCoding 依赖过期。如果我只跑一条链，无论信了谁，都会在错误的路上浪费半天。这件事让我意识到一个一直被我忽略的事实：**LLM 的判断是概率采样，同一道题跑两次，结果真的可能不一样。**

黄佳老师《Agent 设计模式之美》第 19 讲「并行探索」把这层窗户纸捅破了：单跑一条推理链，等于赌这一次采样刚好采到对的那条路径。这道题，值得展开讲讲。

---

## 为什么要"同时跑几条路"？

先理解一个反直觉的事实：LLM 的推理是概率生成。temperature 不为零的时候，每次解码走的路径都可能不同。题目简单时无所谓，怎么采样都能采到对的答案；题目一难，答案的分布就散开了。单跑一条链，你拿到的只是这个分布里的一个采样点——至于分布本身有多宽、这一次采样偏不偏，你完全不知道。

并行探索的做法，是对同一个问题展开多条独立的推理路径，让每条路径带着自己的口径、证据和结论回来，再通过聚合、验证器和分歧裁决，把结果收束成自动判断、弱通过、人审或重新路由。它的本质是**用多样性换可靠性**——用多条样本去逼近那个分布，得到比单次采样更稳的结论。

这个思想在机器学习里不陌生：集成学习用一堆有差异的弱模型投票。到了 LLM 时代，Self-Consistency 论文把"采样多条推理路径再选最一致的答案"引入了推理过程。但对执行型 Agent 来说，并行探索不能只停在"多采样几次"——光有随机性不够，真正要强调的是**证据、裁决和分歧**。

## 核心框架：三种形态，五层结构

### 三种形态：路径是怎么造出来的

| 形态 | 做法 | 适合场景 | 代表 |
|------|------|---------|------|
| 采样投票 | 同 prompt 采样 N 条 CoT 链，投票 | 有明确标准答案：数学、分类、抽取、单一口径规则判断 | Self-Consistency |
| 结构化搜索 | 推理展成树，每步生成多个候选，自评、剪枝、回溯 | 需要前瞻、试错、规划、搜索 | Tree of Thoughts |
| 多视角并行 | 几条路径各按一个**业务口径**推同一件事 | 口径多、制度解释多、证据各异的判断 | 执行型 Agent 最该重视 |

最值得强调的是第三种。奖金该按哪版政策算？旧版有效期口径、新版发放时点口径、审批日期切换口径——三条路背后都有证据、都有制度解释。这种问题靠采样投票解决不了：你把同一个 prompt 采样 10 次，如果它们都默认用了"发放月口径"，那 10 条链只是同一个前提下的 10 次复读。真正需要的是**业务口径的多样性，而不是随机性的多样性**。

### 五层结构：广度诊室的工程实现

**第一层，接住路由结果。** 上一讲的分诊台把任务送进来时，RouteDecision 至少要带：`lane = structured_reasoning`、`reasoning_mode = PARALLEL`、`max_paths = 3`、`human_gate`、`budget`。关键设计是 lane 和 reasoning_mode 继续分开——PARALLEL 只说明这次怎么推理，绝不说明能不能写库、能不能自动放行。能不能动手，永远由 lane、risk 和 human_gate 决定。

**第二层，口径注册表（LensRegistry）。** "请从多个角度分析"这种 prompt 没有技术含量——模型现场编出来的角度没有出处，验证器没法查，审计时说不清当初为什么按这个口径算。每个口径应该登记：lens_id、口径名称、政策出处、适用条件、需要哪些证据、默认验证器、风险等级。模型可以提议新口径，但不能直接进自动判断，必须说明来源、经人审确认才能入册。口径是业务资产。

**第三层，路径隔离。** 多条路径要独立，工程落点就是上下文隔离：三条路径各拿自己的口径、证据要求和验证器，中途不共享中间结果。模型分析第二个口径时，不该看见第一个口径的结论。并行探索的可靠性来自路径之间的差异和独立——路径互相污染，投票和聚合就会产生虚假的置信度。

**第四层，每条路径是一条 mini 可验证链。** 路径产出是结构化的 PathResult，至少包含：lens（用的哪个口径）、claim（结论）、normalized_claim（规范化结论）、evidence_refs（凭什么）、validator、validation_status、confidence。注意 claim 和 normalized_claim 必须分开——"9600 元""9,600""旧版口径金额 9600"语义可能是同一个答案，自然语言不能直接投票，聚合前必须先归一化。还要强调：模型自评置信度只是弱信号，薪酬、税务、权限这类任务，真正能放行的是证据和验证器。

**第五层，聚合分级，分歧落盘。** 最省事的是多数投票，但多数投票有个危险本能：它总能投出赢家。对执行型 Agent 这很危险——有些分歧不是噪声，而是真实的制度分歧，硬投成赢家就是把不确定性盖住了。生产里的聚合应该分级：

- 全部一致 → 自动产出判断
- 多数一致但存在异议 → 只读分析可弱通过并标注异议；高风险写入必须看 human_gate
- 平票、三方分裂、关键路径失败 → 转人审或重新路由
- 证据缺失、验证失败 → 不聚合，先补证

聚合完成后，整趟并行探索写进 ReasoningTrace：mode、path_specs、path_results、aggregation_decision、disagreement_level、winning_path_ids、dissenting_path_ids、failed_path_ids、stop_reason。口径分歧本身就是审计事件——是 Agent 向人类汇报成果的一部分，并不一定要选出一个"最正确的结果"。

### 代码骨架里最值得学的三个设计

文章给了一份最小生产级骨架，我挑三个最戳我的点：

**can_vote() 闸门**——不是所有路径都有资格投票：

```python
def can_vote(self, require_validation: bool = True) -> bool:
    if self.status is not PathStatus.SUCCESS:
        return False
    if not self.normalized_claim:
        return False
    if require_validation and self.validation_status is not ValidationStatus.PASSED:
        return False
    return True
```

工具失败、证据缺失、验证器没过的路径，不能和有效路径拥有同样票权。这比我习惯的"所有返回都算数"严谨太多。

**聚合不选赢家，而是裁决分歧**——`aggregate()` 的核心不是 `most_common()` 选第一名，而是先判断有效路径是否足够，再判断是否存在唯一赢家：平票分裂直接转人审，全部一致才自动产出，多数一致要看策略是否允许弱通过。对薪酬税务这类高风险场景，默认策略应该是 `require_unanimous_for_auto=True`——不允许用 2:1 多数直接自动写入。**选不出安全赢家时，verdict=None 本身就是一个正确结果。**

**执行层用 asyncio 隔离失败**——每条路径有独立超时和异常处理，一条路径失败不能拖垮整次探索。真正让路径"跑起来"的不是并发本身，而是前面的 PathSpec 契约、PathResult 回执、验证器状态和聚合策略。

### 一抬一耗：并行探索不该是默认开关

这个模式对生产指标是"一抬一耗"：抬高验证通过率（要么择优选出证据最足的那条，要么把分歧顶到人审，落库的结论质量都更高），消耗单位验证成功成本（N 条链 = N 倍 token）。所以它不该是默认开关，该由分诊台挑场景用——客服分类这种又便宜又有标准答案的任务，开并行何必呢？值不值得付 N 倍 token，要看这类判断错一次的代价有多大。

另外，**分歧率本身是值得盯的观测信号**：某类任务的分歧率突然升高，往往说明这类业务的口径正在变得不稳定——新政策上线、新旧规则交接。并行探索也是业务问题的预警器。

## 对照我的项目

### 1. cua-driver：AX 树会撒谎，我却一直在单跑一条链

我日常用 cua-driver 驱动 macOS 界面，最深的教训是：get_window_state 返回的 AX 树在某些表面上会骗人——Electron 的 echo-confirm、Catalyst 的 null 值、虚拟化列表的 off-viewport 行，树里显示的和屏幕上的真实情况经常对不上。我的排障流程是典型的单链：先信树 → 点击 → 截图发现没生效 → 换坐标再点 → 还不行就 foreground。这是一条链上的顺序重试，每次"重试"其实都在同一个前提（同一个 AX 树）下采样。

对照文章的多视角并行，正确的做法是**双路径交叉验证**：AX 树（role/label/层级）和截图 OCR（像素证据）同时跑，两条路径各拿各的证据，聚合裁决。而且路径隔离在这里有非常具体的含义——我"以为"树是对的之后，再去截图里找支持这个结论的证据，这就是确认偏误，等于让第二条路径看见了第一条的中间结果。可靠的做法是先让 OCR 独立读一遍，再拿两个结果对账。

### 2. dual-track-eval-harness：我有并行雏形，但缺分歧落盘

我有一条双轨评测管线（dual-track-eval-harness）：同一批任务在公网 ChatGPT 和内部生产线上并行跑，对比结果、用评审量表打分。这其实就是真实的多视角并行——两条轨道是两条独立路径，评审量表是验证器。但我对照五层结构检查了一遍，发现缺了最关键的两块：

- **没有口径注册表**：两条轨道的模型、prompt 版本、temperature 都没有登记成可审计的 lens。换过一次模型后，"这次对比的是哪两个口径"只能靠记忆。
- **没有分歧落盘**：对比结果只记"差异"，没有 disagreement_level、没有 dissenting_path_ids。当两条轨道给出矛盾结论时，我只会人工判断"哪个更可信"，从不把"分歧存在"本身记成审计事件。

文章的洞察点醒了我：分歧不是需要消灭的噪声，它本身就是信息。双轨评测里，两条轨道不一致恰恰是最值得写进 trace 的信号——说明生产线的某个环节和公网基线有偏差。

### 3. 每日写博管线：什么时候值得付 N 倍 token

我的每日写博管线是单路径的：一个 agent 消化文章 → 产出一版博客 → 版权审核 → 发布。我有 flash 和 pro 模型的对比实验数据——同一篇素材，两个模型写出来质量差得很远，pro 的比喻和结构明显更高级。但我从来没想过双跑聚合，因为写博客错一次的代价很低，不值得付 2 倍 token。

这正是文章"一抬一耗"的决策框架：**值不值得开并行，看的是这类判断错一次的代价，不是它的难度。** 我的管线里真正高风险的是版权审核（write_sensitive，审核不过就 push 到 GitHub）——这一步如果双跑（两个 agent 独立做版权审核再聚合），性价比远高于让两个模型各写一版博客。而像"客服分类"这种低代价判断，我的系统里对应的是 v2-pipeline 的日常采集——开并行纯属浪费。

### 4. 模型调度：把"路由选一个"升级为"并行跑几个"

我有一条调度原则：重量任务委派 Claude Code 或 Codex。上一讲我反思过这是只看 intent 的粗糙路由，这一讲给了我另一个视角：有些任务不该"路由选一个模型"，而该"并行跑几个再聚合"。

最典型的候选就是开篇那个场景——UE5 编译失败诊断。编译失败这类判断"跑两次结果可能不一样"（头文件循环引用 vs LiveCoding 依赖，两个模型各执一词），而且错一次代价很大（在错误方向上修半天 C++）。这种就该 Codex + Claude Code 双跑诊断，把分歧展示给人看，最终裁决权留在人手里——对应文章的 human_gate = before_write，因为改 C++ 是写敏感操作。而"用户消息里有没有 claude 关键词"这种路由，继续单跑就好，永远不需要并行。

## 我的反思：六个反模式，我踩了四个

文章结尾给了六个反模式，我对照自查，触目惊心：

1. **同 prompt 多采样当多视角** —— 踩了。我经常让同一个模型"再试一次""换个说法再想"，这就是采样投票的滥用，10 次复读同一个前提。
2. **永远强行投出赢家** —— 踩了。两个模型诊断矛盾时，我总想"选一个对的"，而不是接受"这里有分歧"。
3. **模型置信度替代验证器** —— 踩了。UE5 编译诊断里，我信过模型自评的"很有把握"。
4. **不记录异议路径** —— 踩了。我从不记录"另一个模型提出了相反结论"。
5. 绕过分诊台 —— 没踩，但也提醒我：不是所有问题都值得并行。
6. 口径没有注册表 —— 没踩（因为我连并行都没有），但双轨评测的教训说明我随时会踩。

改造清单，按性价比排序：

- **给 cua-driver 加 AX+OCR 双路径交叉验证**：树撒谎时不再顺序 fallback，而是两条路径独立取证、聚合裁决。这个改动最便宜、收益最直接。
- **给双轨评测加分歧落盘**：补 disagreement_level 和 dissenting_path_ids，把"不一致"本身变成审计事件和观测信号。
- **给 UE5 编译诊断加双模型并行**：Codex + Claude Code 各诊断一版，分歧摊开给用户裁决——但先想清楚 human_gate，编译修复是写敏感操作，最终决定权必须在人。

文章里有句话我打算贴在工位上：**普通投票追求选出赢家，并行探索追求裁决分歧。** 我们用了太多 Agent 的人都知道，它们通常都装得很确定——并行探索的价值，恰恰是让它们更诚实地暴露不确定性。下次再看到两个模型自信地给出矛盾结论，别急着选边站，先把分歧本身记录下来。分歧不是 bug，它是系统在告诉你：这件事的水很深。
