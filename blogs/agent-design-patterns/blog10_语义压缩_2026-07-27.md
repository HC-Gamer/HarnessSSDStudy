# blog10: 语义压缩——别让 Agent 在同一个坑里摔两次

今天上午写博客时，为了从 Safari 的 Cookies.binarycookies 里提取极客时间的登录态，我让 Hermes Agent 解析那个二进制文件。第一次尝试，struct 格式写错了——unpack requires a buffer of 56 bytes。我改了一下偏移量再试——unpack requires a buffer of 52 bytes。再改——too many values to unpack。

三次失败之后，我突然意识到一件事：**Agent 第一次失败的方法和第二次失败的方法，在模型眼里几乎是一样的。** 它看不到"struct 偏移量越改越错"这个模式——因为前两次失败的上下文已经被压进了历史摘要，变成了一句模糊的"解析二进制 cookie 文件持续遇到格式错误"。

这恰好是黄佳老师这一讲的核心命题：**坏的压缩，会把关键证据压没。更坏的压缩，会让 Agent 忘记哪些方案已经失败，然后在同一个坑里反复试错。**

---

## 压缩不是摘要

大多数人对 Agent 上下文管理的直觉反应是：满了就压一下。压完了继续跑。

黄佳老师把这件事拆得很清楚——**语义压缩（Semantic Compaction）不是 summarize，而是工作记忆维护。** 他给了一个让我印象极深的类比：特德·姜说过 ChatGPT 是"网上所有文本的模糊图像"。语义压缩的每一层都像暗房里翻拍照片——第一次翻拍主体还在，第二次边缘开始糊，第三次细节永久丢失。

真正生产级的 compactor，黄佳老师拆成了三个层次：

- **Level 1 — 清理冗长 tool 输出**：日志全文、API 响应、查询结果。不是错误信息的话，可以先替换成占位符。
- **Level 2 — 合并进 Anchor**：把旧历史抽成意图、已做改动、已做决策、已排除方案、下一步计划，增量合并。
- **Level 3 — 极限压缩**：只在别无选择时触发。而且 Level 3 应该被视为**退场信号**——session 太长，该交接了。

三层之间的核心逻辑用一张表说清楚：

| 层级 | 触发时机 | 保留什么 | 丢掉什么 | 风险 |
|------|---------|---------|---------|------|
| L1 | tool 输出堆积 | 错误堆栈、关键数字 | 日志全文、API 原文 | 低 |
| L2 | context 60-70% | Anchor 五字段 | 旧对话原文 | 中 |
| L3 | 窗口紧急 | 最少核心证据 | 大量历史 | 高 |

## 我在 Hermes Agent 里看到的三个问题

读完这个框架之后，我拿它审视了自己正在用的 Hermes Agent——然后发现了一些相当具体的对应。

### 问题一：上下文的 MEMORY 区是静态压缩

Hermes Agent 在每次系统 prompt 里都放入一块 MEMORY 区域，大小控制在约 2200 字符。这是一个**手工维护的压缩**——我每次发现重要的约定就加进去，太久没用的就删掉。

但这个过程有两个痛点。

第一个是它**没有分层**。我把"UE5 怎么启动"和"GitHub 双账号配置"和"CyberCycho 和正宗Gamer 不互相引流"混在一起，全部平铺在一个文本块里。它们的重要性完全不同：UE5 启动参数错过一次，也就是引擎起不来；CyberCycho 的品牌隔离规则错了，是内容策略级事故。

第二个是它**没有 excluded_approaches**。MEMORY.md 里记录了"不要用 `-log` with Hermes terminal"——这是一个排除项。但它是靠人手工写进去的。如果模型在某个 session 里发现"不要用某种方式启动 UE5"，这个信息除非我手动加进 MEMORY.md，否则下一个 session 从头开始。这意味着**跨 session 的 excluded_approaches 完全靠人力维护。**

### 问题二：错误循环的"失忆"

我在日常用 Hermes Agent 做开发时，最常见的翻车场景是这样的：

Agent 调用 terminal → 编译失败 → 读错误日志 → 修代码 → 再编译 → 又失败 → 再读日志 → 再修。

如果这件事在 6-8 轮内解决，没问题。但如果在第 15 轮还没解决，问题来了——**第 3 轮试过的那个 patch 方案，和第 15 轮要试的方案，在压缩后的历史里看起来完全不同。** Agent 不知道"这个方案第 3 轮就已经排除了"。

黄佳老师提出的 Anchor 结构里，`excluded_approaches` 这个字段不是锦上添花，而是**防止 Agent 在长 session 里退化成随机试错**的最后一道防线。

对应到 Hermes Agent，现在的 skills 系统可以部分充当跨 session 的 excluded_approaches——比如 `ue5-macos-editor-debugging` 技能里记录了各种已排除的启动方式。但**in-session 的 excluded_approaches 仍然缺失**。在同一个 session 里 Agent 学到"别用 struct 格式 I4xIIIIIIIIdd，要用 I4xIIIIIIIdd"，这个消息活不过下一次上下文压缩。

### 问题三：ObservationMasking 的思路在 Hermes 里能怎么用

黄佳老师分析了 OpenHands 的 ObservationMasking 设计：Agent 历史里有两类信息——Action（做了什么）和 Observation（外部返回了什么）。ObservationMasking 把早期 Observation 替换成占位符，但保留 Action。

这直接对应 Hermes 的一个常见模式：

```
Action: terminal("grep -r 'some_pattern' /src/")
Observation: [2400 行匹配输出]
Action: read_file("/src/module_a.py")
Observation: [1500 行代码]
```

2400 行 grep 输出和 1500 行代码本身不是"认知"，但 Agent 需要记住"我搜过这个模式、读过这个文件"。ObservationMasking 的做法是在后续轮次里把 Observation 替换成 `<observation-ref:tool_call_3>`，只在 Agent 明确需要时才展开原文。

这比通用 LLM summarization 更稳的原因是：**它不引入语义漂移。** LLM 摘要可能把"搜索返回了 2400 行匹配"理解成"有大量相关代码"，而丢失了"具体是哪些文件"这个信息。ObservationMasking 保留了一个回退路径——handle 还在，只是不占 token。

## 如果让我设计 Hermes 的 Compaction 层

基于这三个问题，我会怎么给 Hermes Agent 加 compaction？

### 第一步：给 MEMORY 加重要性标记

现在是纯文本块。改成带分类的结构：

```
[CRITICAL] UE5: PythonScriptPlugin 预编译 → C++ 插件不能从源码编译
[CRITICAL] GitHub 双账号：HC-Gamer（默认）和 patrickhuangcheng（UE5）
[IMPORTANT] CyberCycho 与大正Gamer 不互相引流
[ROUTINE] blogs 目录结构
```

当 context 压力大时，CRITICAL 项优先保留，ROUTINE 可以压成一句摘要。

### 第二步：in-session excluded_approaches

在每次 terminal 失败后，自动记录 `[EXCLUDED] {approach}: {error_summary}`。在下一次上下文压缩时，这个列表比普通对话历史更优先保留。

具体实现上，可以用最简单的方案——在 MEMORY 区域尾部加一个动态段：

```
## Session Excluded Approaches
- struct格式 `I4xIIIIIIIIdd` → unpack requires 52 bytes
- binarycookies offset+60 → overshoot
- JXA doJavaScript syntax → Named parameters error
```

不需要完整的 CompactionEvent 对象，几个字节的结构就能防止 Agent 在同一个坑里反复试错。

### 第三步：ObservationMasking for Terminal Output

Hermes Agent 大量使用 terminal 工具。terminal 的返回经常是几百上千行的日志或代码。我的想法是：

- 如果 terminal 返回以 `error:` / `Traceback` / `FAILED` 结尾，原文保留。
- 如果 terminal 返回是普通成功输出，保留前 5 行和后 3 行，中间替换成 `<omitted N lines>`。
- 所有被省略的输出保留一个 handle（比如写到临时文件），Agent 需要时可以重新展开。

## 压缩是一种认知

这一讲里最打动我的一句话是：**"好的压缩本身就是一种认知。你 Agent 选择保留什么，决定它接下来能想清什么。"**

我之前一直以为上下文管理是"窗口不够了怎么办"的工程问题。读完这一讲，我的认知被刷新了：**它本质上是一个认知问题。**

一个学生能把整章内容总结成一段话，说明他真的理解了这一章。一个 Agent 能把自己的对话历史压缩得既精炼又保留关键证据，说明它仍然理解自己在做什么。坏的压缩不只是工程缺陷——说明系统已经分不清什么是背景噪声，什么是关键证据。

而 Martin Fowler 那句"重构的安全感来自测试覆盖率"，被黄佳老师用在这里特别妙：**语义压缩的安全感，来自关键证据的保护——尤其是错误堆栈和失败记录。** 错误堆栈就是 Agent 的测试套件。把错误堆栈压成一句模糊的"出现了错误"，就像重构时顺手删掉了测试。

我自己的体验完全印证了这一点。用 Hermes Agent 做 UE5 编译调试时，编译错误的存在本身就是最重要的上下文——它告诉 Agent 问题出在哪一行、哪一类、哪个模块。丢失了这种信息，Agent 就只能在七八种可能的修复方案里靠猜来选。

---

## 总结

语义压缩解决的核心问题只有两个：**什么时候压？压的时候必须保留什么？**

生产级 compactor 不是 `summarize_history()` 函数，而是分三层、带 Anchor、可观测的工作记忆维护系统：

1. **自动触发**：不要等窗口满了再压，在 60-70% 就该动手。
2. **分层处理**：先清理 tool 输出，再合并 Anchor，最后才极限压缩。越往后越激进。
3. **保存 Anchor**：意图、已做改动、已做决策、已排除方案、下一步。不是摘要的摘要的摘要。
4. **保护错误**：错误堆栈、关键数字、文件路径、行号不能丢——它们是 Agent 的测试覆盖率。
5. **可观测**：每次压缩留下事件记录。如果 Agent 后面变蠢了，你得知道是哪一次压缩把线索压没的。
