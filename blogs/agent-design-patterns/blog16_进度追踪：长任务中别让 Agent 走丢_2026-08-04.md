# 长任务中别让 Agent 走丢——进度追踪的五个工程支架

每周一下午 5:00，我的 macOS crontab 会准时触发一条命令：`hermes chat --profile deepseekco -q "运行每日写博管线"`。这条管线要做的事看起来不多——读一篇文章、消化成笔记、写一篇博客、更新追踪文件、推送到 GitHub——总共也就五步。但如果你看过它的日志，你会发现它其实脆弱得要命：Cookie 过期了怎么办？API 返回空内容怎么办？博客写得质量太差怎么办？文件路径写错了怎么办？

这些问题，每周都在发生。而我的解决方案，刚开始只有一句 `set -e`。

这篇文章要聊的，就是"让 Agent 跑几十步、上百步还不跑偏"这件事。这是黄佳老师《Agent 设计模式之美》专栏的第 14 讲——进度追踪（Progress Tracking），记忆模式组的第三个具体模式。

---

## 人类团队怎么不跑偏？

先退一步看人类团队。一个长周期软件工程任务——比如"把薪酬系统的异常核验流程补齐，让 6 月批次能上线"——是怎么推进的？

周一开会分任务，有人核对规则，有人接口联调，有人补测试，有人准备人审清单。到周三，写接口的在 debug 一个权限报错，越陷越深；补测试的在顺便清洗历史数据；负责规则的被拉去开另一个会，回来忘了上次讨论到哪一步。

但人类团队通常不会彻底散掉。因为我们有一套"防跑偏装置"：

- **会议纪要**把原始目标重新固定下来：我们要交付的不是所有问题都解决，而是让 6 月批次能进入人审
- **项目计划**把长目标拆成阶段：现在是"异常核验"，不是"完整规则治理"
- **任务清单**告诉你还有什么事没做
- **测试清单**告诉你事情做完没有
- **审批节点**拦住高风险动作
- **同事提醒、code review、晨会同步**不断把局部工作拉回全局目标

核心洞察：**人不是靠脑子记住一切，人是靠一整套外部化支架，才把一个长项目稳稳推进下去的。**

Agent 缺的就是这套支架。

## 五个最常见的"走丢"方式

在我的日常管线里，Agent 走丢的方式有好几种，每一种都对应一个经典问题。

**1. 目标漂移。** 有一天管线在消化一篇 22K 字的长文。Agent 读着读着，被文章里一个具体的代码示例吸引了，开始深挖这个示例的技术细节，最后产出的博客变成了一篇"如何实现这个具体功能"的教程——完全忘了原来的任务是"消化这篇文章的核心框架然后对照自身项目写博客"。局部目标越来越具体，最终替代了全局目标。

**2. 状态漂移。** 另一个场景：Agent 以为 `article-chain.toml` 已经更新过了，于是跳过更新步骤直接 git commit。结果下次 pipeline 运行时，又去处理同一篇文章。Agent 对世界的记账错了，但目标看着没错——这种 bug 最难排查。

**3. 上下文污染。** 当 Agent 同时处理多篇文章的消化任务时，前一篇的关键词（比如"RAG"）会残留在上下文里，让下一篇的消化带上了错误的预设。长对话窗口里，越靠前的信息污染越严重。

**4. 过早完成。** 有一次，管线产出的博客正文只有 300 字。Agent 觉得"我写完了"——文件存在、git commit 成功、一切正常。但 300 字的博客显然不满足质量标准。Agent 没有自我验证的能力。

**5. 没有恢复入口。** crontab 触发时，上一次的管线可能因为网络问题在第三步失败，但没有任何状态保留。新一轮管线重新从第一步开始，完全没有"上次做到哪了、为什么失败、应该从哪继续"的记忆。

这些问题的共同特征是：没有 Agent 是故意跑偏的。**迷失是一点点积累出来的，很少一步崩掉。**

## 五个工程支架：把我的管线对号入座

黄佳老师把进度追踪拆成五个工程组件。让我用一个贯穿的例子——我的每日写博管线——来看每个组件是怎么落地的。

### 支架一：目标契约（Target Contract）

> 一份不断自我提醒的会议纪要：要交付什么、不要交付什么。

这个组件解决的是"**我到底在干什么**"。

在我的系统里，目标契约就是 **geektime-to-blog 技能文件本身**。每次运行管线，Agent 做的第一件事是 `skill_view(name='geektime-to-blog')`——加载这份"会议纪要"。这个文件明确写了：

- 要交付：一篇博客（从 article-chain.toml 取下一篇，用 Cookie 获取文章，消化成博客，更新链，git push）
- 不要交付：不要把 is_freelyread=true 加进 API 请求（会导致付费内容返回空）；不要把训练营文章和专栏文章搞混
- 边界：此技能仅用于 Agent 设计模式专栏，不处理 Harness 学习系列

这个文件是我和 Agent 之间的"契约"。每次管线启动，Agent 先读它，就像周一早上重新看一眼会议纪要一样。

**在 UE5 项目里同理。** 当我让 Agent 编译一个 C++ 项目，目标契约就是"编译成功，Launch 起来"。它不关心 shader 警告、不关心 deprecation notice——那些不是这次编译的目标。没有这个契约，Agent 就会被几百行 warning 牵着走。

### 支架二：里程碑（Checkpoint Milestones）

> 把长任务拆成阶段，每个阶段有明确的完成信号。

这个组件回答"**现在到哪了**"。

我的管线用的是 **article-chain.toml**。文件里有一个 `remaining` 列表：

```toml
remaining = [
  [16, 990515, "14｜进度追踪", 22000],
  [17, 991831, "15｜失败日记", 24000],
  ...
]
```

第一项就是"当前里程碑"。处理完这篇，就从列表移除，第二项变成新的当前里程碑。每个里程碑有四个参数：博客编号、文章 ID、标题、字数——不是随便写的，字数直接决定了消化策略（22K 字的需要更长的上下文窗口）。

Agent 每跑一轮都清楚自己在本系列的第几个里程碑上，还剩多少篇。这就像项目计划里的甘特图，只不过 Agent 的版本只有一维：**沿着一根链往前走**。

**在 v2-pipeline（多 Agent 研究管线）里也用到了这个模式。** 研究任务拆成 milestone 列表：

```python
milestones = [
    {"stage": "gather", "done": False, "signal": "raw_notes written"},
    {"stage": "analyze", "done": False, "signal": "analysis_draft written"},
    {"stage": "report", "done": False, "signal": "report.html published"},
]
```

每完成一个阶段，Agent 必须在进度账本里标记 `done: true`，才能进入下一阶段。一个 milestone 没完成就想跳去下一个？不存在的。**没有完成信号 = 没完成，这是工程纪律。**

### 支架三：进度账本（Progress Ledger）

> 一份工作日志，记录关键决策、证据和下一步动作。

这个组件存储"**我做了什么、为什么要这样做**"——不只是 what，更是 why。

在每日管线里，进度账本有两层：

**表层：article-chain.toml 的状态变量。**

```toml
last_processed_id = 989200
last_processed_title = "13｜检索增强"
last_blog_number = 15
```

这是"现在到哪了"的简洁答案。

**深层：Git 提交历史。**

```
blog15: 13｜检索增强 → blog14: 12｜分层保留 → ...
```

每次 `git commit` 都带上了标题，这就是一份完整的进度日志。万一管线中断，我可以用 `git log --oneline` 直接定位到上次成功处理的文章。

但这里的核心教训是：**进度账本不是日志文件。** 日志是"执行了什么"（调了 API、写了文件、推送了代码），进度账本是"做了什么决策、为什么"（选了哪种消化策略、为什么这篇文章用了 Opus 而上一篇没有、遇到了什么坑、下一步要注意什么）。

一个真正有用的进度账本，应该让下一轮 Agent 读了之后，不需要重新推理就能接续工作。就像同事交接任务时，你不会给对方看一整本 syslog，而是给一张便签："上次改到 auth.py 第 347 行，还有一个 edge case 没覆盖，记得跑 `test_auth_edge_cases.py`。"

**在我的 UE5 编译流程里，这个模式已经被固化成技能。** `ue5-macos-editor-debugging` 技能里记录了每次编译失败的原因和修复方案：`-Wshadow` 警告、LiveCoding 依赖、`.generated.h` 缺失——这些不是一次性 bug，而是反复出现的 pattern。每次编译 Agent 先查这份"病历"，比从头推理快十倍。

### 支架四：验证闸门（Validation Gates）

> 测试清单和审批节点，防止"看着做完了，其实没验收"。

这个组件保证"**做的对不对**"。

在管线里，我设计了这几道闸门：

| 闸门 | 检查点 | 不通过怎么办 |
|------|--------|-------------|
| 获取文章 | `Content length > 0` | 检查 Cookie 是否过期，或降级到离线缓存 |
| 消化博客 | 博客正文 ≥ 1500 字 | 重新消化或换模型 |
| 版权审查 | 原文引用 < 50%，项目经验 ≥ 50% | 重写薄弱段落 |
| 更新链文件 | `last_processed_id` 已变更 | 手动修复 article-chain.toml |
| Git 推送 | `git push` 返回成功 | 检查 SSH key 或网络 |

最初我的管线没有这些闸门。结果有一天，Cookie 过期了，API 返回空内容，Agent 拿空字符串去做消化——然后真就生成了一篇博客："这篇文章讨论了...内容暂无。"还 git push 上去了。那一刻我意识到：**没有验证闸门的 Agent 管线，就像没有测试的 CI 管道——看起来在跑，实际上在造垃圾。**

加了闸门之后，管线行为完全变了。Cookie 过期 → 闸门 1 触发 → 整个管线 halt，留下一行日志："Article fetch failed: empty content, check cookie."而不是继续往下跑，把错误传播到博客仓库。

**注意，这些闸门的核心设计原则是：不通过就停。** 不降级、不跳过、不"先跑着后面再说"。因为进度追踪模式的前提假设是：错误的步骤会污染后续所有步骤。一个错误通过之后，后面十步都在这个错误上搭楼。

### 支架五：漂移哨兵（Drift Sentinel）

> 一套自动监控机制，持续检查 Agent 是否偏离了原始目标。

这个组件监控"**还在正确的轨道上吗**"。

漂移哨兵是最微妙的一个支架，因为它需要一个"旁观者"视角——Agent 自己很难判断自己有没有跑偏，毕竟如果它知道自己在跑偏，它就不会跑偏。

在我的系统里，漂移哨兵的实现分三层：

**第一层：技能固化的目标契约。** 每次管线启动，Agent 必须先 `skill_view` 加载技能文件。这不是多余的步骤——这是漂移哨兵的基础形式。技能文件里写了"要交付什么"、"什么不要做"、"常见的 Pitfall"，Agent 每读一次就重新对准一次目标。

**第二层：结构化的进度账本。** article-chain.toml 不是纯文本日志，而是结构化的 TOML。Agent 可以直接从 `last_processed_id` 和 `last_blog_number` 推断当前进度，不需要解析自由文本。结构化本身就是一种漂移防护——模糊的日志容易被误解，结构化的状态不会。

**第三层：外部护栏。** crontab 本身就是一个漂移哨兵。每天同一时间触发，不管上次跑成什么样。如果上次管线在第三步挂了，新一轮 Agent 会从 article-chain.toml 读到"上次处理到 blog15"，然后自动处理 blog16——不需要人工干预。**定时触发 + 结构化状态 = 自动恢复。**

## 我在实践中补的一课：进度追踪的"粒度"问题

用这套框架跑了两个月管线之后，我发现一个原文没深入讨论但实践上至关重要的问题：**进度状态该有多细？**

刚开始，我的 article-chain.toml 只有一个 `last_processed_id`。管线中断后，Agent 只能知道"上次处理完的是 989200"，但完全不知道中断时正在进行什么操作——是在消化文章、在写博客、还是在 git push？不同阶段的恢复成本完全不同。

后来我把进度账本细化到：

```toml
pipeline_state = {
  stage = "write_blog",      # 当前阶段
  article_fetched = true,    # 文章已获取
  digestion_done = true,     # 消化已完成
  blog_written = false,      # 博客正在写
  chain_updated = false,
  git_pushed = false,
}
```

这样中断后恢复时，Agent 知道自己已经完成了获取和消化，只需要继续写博客，不需要从头重做。

但这个粒度的代价是：**每完成一个子步骤就要写一次文件。** 如果粒度过细，I/O 开销会超过任务本身。如果粒度过粗，中断恢复又不够精确。这里的工程取舍是：**以"重新做不痛苦"为底线。** 文章获取要 3 秒、消化要 30 秒、写博客要 15 秒——总共不到一分钟。所以即使恢复到粗粒度（从头重做），损失也是可接受的。如果你的任务单步就要 10 分钟（比如训练模型、编译 UE5 项目），那粒度就必须更细。

## 五个支架之间的关系

这些支架不是独立的。它们是一张网：

```
目标契约 ──► 里程碑 ──► 进度账本
    │           │           │
    └───────────┼───────────┘
                ▼
          验证闸门 ◄── 漂移哨兵
```

- **目标契约**定义"要做什么"，**里程碑**把它拆成阶段
- **进度账本**记录执行轨迹，**漂移哨兵**持续对照账本和契约，检测偏离
- **验证闸门**在关键节点执行检查，不通过就停——它是漂移哨兵在"点"上的表现形式，而漂移哨兵是验证闸门在"线"上的持续监控
- 五个支架**缺一个，整个系统就会有盲区**。没有目标契约 = 不知道自己在跑偏；没有里程碑 = 不知道跑到哪了；没有账本 = 中断后无法恢复；没有闸门 = 错误会传播；没有哨兵 = 偏了也不知道

---

## 总结：Agent 不是缺"努力"，是缺"框架"

真实跑过 Agent 长任务的人都会有这种感受：**Agent 不懒，它很勤奋。它的问题是勤奋用错了地方。**

它不是不想完成任务，它是被一个 import error 吸引了全部注意力，忘了自己在重构 auth.py。它不是没有产出，它产出了 300 字的博客，然后觉得够了。

这篇文章的核心框架——目标契约 + 里程碑 + 进度账本 + 验证闸门 + 漂移哨兵——本质上不是在教 Agent "怎么更努力"，而是在教我们"怎么给 Agent 补上人类工作中那套默认存在的外部化支架"。

在我的每日写博管线里，这五个支架分别对应了：geektime-to-blog 技能文件（契约）、article-chain.toml 的 remaining 列表（里程碑）、last_processed_id + git log（账本）、每步的检查条件（闸门）、crontab + 技能加载（哨兵）。它们一起，把一个"每天看运气能不能跑完"的脚本，变成了一个"中断了也知道怎么续"的系统。

换个角度想：**进度追踪不是为了跑得快，是为了跑得远。** 如果你只是让 Agent 跑 3 步就结束，你不需要进度追踪。但如果你想让它跑 30 步、300 步——那就必须在每一步结束后，给下一步留下足够精确的上下文，让它知道"我在哪、要做什么、上次发生了什么"。
