# 推理模块导论：让 Agent 想得清楚，也想得起来

我调度模型的方式，曾经粗暴得像个按菜谱炒菜的学徒：不管是问天气还是做架构设计，统统塞给同一个模型。

后来我给自己定了一条调度规则——轻活交给 DeepSeek 编排分发，重量任务（研究、代码生成、深度分析）才委派给 Claude Code 或 Codex CLI。当时我以为这就是"优化成本"，直到我读到黄佳老师《Agent 设计模式之美》第 16 讲——推理模块导论，我才发现自己摸到的只是一张完整调度台的第一块旋钮。这篇文章，就是我把"推理"从一个模型能力重新理解成"一种需要调度和约束的计算资源"的完整过程。

---

## 为什么要研究推理？先回答一个问题

感知模块解决"Agent 看见了什么"，记忆模块解决"Agent 留下了什么"，推理模块回答的是最后一个问题：**面对眼前的信息和过去的经验，该相信什么、该选择什么、该做什么。**

用我自己系统里的一个真实场景说：夸克网盘账号被封禁后，转存/下载 API 全部返回 401 guest。感知层拿到了"请求失败"这个事实，记忆层里有 quark-pan-download 技能记录着"该换有效账号"。但真正的决策——是重试、换账号、还是放弃这条下载路径——是推理层的事。

我过去犯的错是：把"决策"和"生成"画了等号。模型吐出一段理由充分的文字，我就当它真的想清楚了。

但文章点破了一个我长期忽略的事实：**模型内部到底想了什么（内部推理），和系统组织出来的外部慎思过程（假设、查工具、比较证据、调验证器），和供工程师审计的决策记录（看过哪些证据、为什么升级），是三件完全不同的事。** 尤其不能把一段看起来有条理的自然语言，当成模型真实计算过程的证明——OpenAI 早期的推理模型特意不暴露思维链，Anthropic 的研究也发现 CoT 并不总是忠实披露真正影响答案的信息。

这让我想起 Hermes 里的一条硬规则：get_window_state 默认带 base64 截图会塞爆上下文，必须用 include_screenshot:false + 落盘。这条规则不是我"推理"出来的，是我被塞爆上下文后写进记忆的——它是一条外部决策记录，而不是一次模型内心独白。

## 核心框架：给"很会猜的推理器"装上边界、仪表盘和刹车

文章从推理的来龙去脉讲起：人类的推理从生存经验开始（乌云→下雨），亚里士多德把它整理成三段论，计算机时代又走过了 Logic Theorist、GPS、STRIPS、MYCIN 专家系统的路。传统推理的核心是"规则清楚、过程可解释"——输入相同、规则相同、输出就相同，程序本身就是证明。

但专家系统没有引领人工智能时代，根源在于规则需要人工编写，面对复杂世界维护成本太高。LLM 把模式压进权重，灵活得多，却带来了概率性、不透明和不稳定——同一个输入重复执行可能走出不同的中间路径。

文章给了一个我特别认同的比喻：

> **LLM 给了我们一个很会猜的推理器，Harness 工程系统要做的，是给这个推理器装上边界、仪表盘和刹车系统。**

这句话把"推理工程"从玄学变成了工程学。它不是要我们写更长的思维链，而是要回答五组问题——文章称之为**推理契约（Reasoning Contract）**：

| 问题 | 我的理解 |
|------|---------|
| 是否启动深入思考？ | 这个请求直接回答是否已经足够？ |
| 采用哪种推理拓扑？ | 沿一条链推进、并行尝试，还是循环调查？ |
| 投入多少预算？ | 最多用多少 token、时间、模型调用、工具调用？ |
| 由什么验证？ | 单元测试、业务规则、外部数据、人工审批，还是另一个模型？ |
| 什么时候停止？ | 达到什么证据标准后输出，出现什么情况后升级或放弃？ |

配套的是一个显式的预算包：`max_thinking_tokens`、`max_latency_ms`、`max_model_calls`、`max_tool_calls`、`max_parallel_paths`——计算预算（test-time compute）是可以被显式管理的维度，答案稳定之后就该停止消耗 token。

四种推理模式对应四种计算拓扑：**思维链（CoT）**拆解出可检查的链、**复杂度路由**按信号分流、**并行探索**广着想多条路径、**迭代假设验证**深着查逐步收敛。文章把复杂度路由比作分诊台，其余三个是诊室；控制链是"先路由再推理，推理后验证，验证不通过换路，达到停止条件才输出"。

最后是四个健康指标：验证通过率、首次路由命中率、单位验证成功成本、推理漂移率——而且必须按任务类型分桶，客服分类、代码修复、财务审批各有各的基线和 SLO。

## 对照我的项目：一张调度台的四次对号入座

### 1. 复杂度路由 ↔ 我的模型调度规则

我早就在做"路由"，只是做得极其原始。我的记忆里写着：DeepSeek 调度/编排/分发，重量任务（研究、代码生成、深度分析）委派 Claude Code 或 Codex CLI。task-router 技能的规则是"默认路由所有任务给 Codex CLI，除非用户说 claude 才走 Claude Code CLI"。

对照文章，我的路由是**关键词路由**——用户提到 "claude" 这个词，就换执行器。这属于文章说的信号之一，但只覆盖了"意图"这一个维度。真正的复杂度路由还要看证据状态（信息够不够）、机械状态（系统忙不忙）、动作风险（这个操作会不会改坏生产数据）。我缺的是后面三个信号，以及一个"路由错了怎么办"的兜底——文章说大量请求最后升级到迭代模式说明低估任务难度，大量低风险请求一开始就进高成本并行搜索说明过度推理，这俩指标我一条都没量过。

### 2. 推理契约 ↔ 每日写博管线的预算实践

我的极客时间写博管线每天 17:00 由 crontab 触发，这条管线事实上已经隐含了一张推理契约，只是没有写成显式的：

- **是否深入思考**：付费文章直接用 Cookie 认证 API 拉全文，不需要让模型猜；
- **预算**：terminal 调用设 timeout，管线有明确的失败出口（Cookie 过期返回 HTTP 452 就停，不无限重试）；
- **验证**：版权审核清单——原文引用 < 50%、自身经验 ≥ 50%、标注出处，这就是业务规则验证器；
- **停止条件**：article-chain.toml 的 remaining 为空就自动终止，neighbors.right 为空说明专栏没发布新文章，管线退出。

最有意思的是"验证不通过换路"：文章说 CoT 走不通要换路，我的管线是——Cookie 过期时从 API 获取切换到离线缓存目录，或者用 Safari AppleScript 提取。这些"换路"动作以前被我当成临时补丁，现在看其实就是推理契约里的"升级路径"。

### 3. 推理追踪 ↔ 我的记忆与技能沉淀

文章说追踪推理，不要记录模型的 thinking 内心戏，而要记录**外部可核验的决策事件**：每一步验证了什么命题（hypothesis）、引用了哪些证据（evidence_refs）、执行了什么动作、环境返回了什么观察、最后为什么停。

这几乎就是我记忆系统的工作方式。我的记忆里存的是："CUA driver 权限用 `hermes computer-use install` 安装，permissions grant 等待 TCC 对话框预期 timeout 124"——这是 hypothesis + observation + decision 的浓缩体。技能库里存的 quark-pan-download 下载流程、macos-keyboard-remap 的 Karabiner 配置，全部是"证据引用 + 动作 + 结果"的结构，而不是一段"我当时是怎么想的"的长篇内心戏。

区别很重要：内心戏不可核验，决策事件可以。下次任务读到技能时，它拿到的是可执行的路径，不是模型的自圆其说。

### 4. 迭代假设验证 ↔ 双账号内容策略的每周循环

双账号内容策略报告我每周更新一次：生成新报告覆盖主文件，同时存档到 reports/2026-W{NN}.md。这个动作的本质就是迭代假设验证——每周围绕"两个账号分别发什么内容"提出假设，观察数据，下一轮修正假设。它不是一个一次性的推理，而是一个"观察改变假设、假设驱动行动、行动产生新观察"的循环。

对照文章，我意识到这个循环缺了显式的"停止条件"：我每周都跑，但没有定义"什么证据标准出现后，这个假设就算验证完毕，不需要再改了"。这正好是文章思考题里问的：长任务跑到第十步，还记得第一步定下的约束吗？

## 我的反思：推理漂移率是最容易被忽视的指标

四个健康指标里，最戳我的是**推理漂移率**——长任务推进中，目标、约束、已验证的事实是否被逐渐遗忘或改写。

我的系统里有一个活生生的例子：极客时间双系列（Agent 设计模式 + HarnessSSDStudy）必须独立运营、互不互相提及，这是写在记忆里的一条硬约束。但这条约束是在任务开始时定的——如果哪次长任务跑到第十步，我"顺手"在一篇 ADP 博客里提了一嘴 Harness 学习系列，那就是一次真实的推理漂移：约束还在，执行忘了。

文章给的解法很具体：在 trace 里加上 hypothesis 和 evidence_refs，让"事实和规范是什么时候被悄悄改写的"变得可审计。这比"相信模型记得住"可靠得多——因为模型本来就记不住，能记住的是外部化、可核验的决策记录。

另一个反思是"单位验证成功成本"：便宜模型反复失败、重试、升级，最终可能比直接上顶配更贵。我过去为了省 token 用便宜模型处理复杂任务，失败后重试两三次再升级，账单没省多少，延迟翻倍。文章说"用最少的充分计算得到可验证的正确决定"——充分二字是重点，省过头就是不充分。

## 总结

推理工程不是制造更长的思维链，而是调度一条最短、充分、可验证的决策路径。四种模式本质上是四种经济学选择：

- 思维链用 token 换取问题分解；
- 复杂度路由用轻量判断换取整体成本下降；
- 并行探索用更多计算路径换取对单一路径偏见的抵抗；
- 迭代假设验证用更多轮次换取在未知环境中逼近真相的能力。

没有一种方式永远最好。该快时快、该深时深，并且每个重要结论都能回到证据上——这是我接下来会照着检查自己系统的四句话。

下一步我会做三件事：第一，把模型调度从关键词路由升级成信号路由，至少加上"证据状态"和"动作风险"两个维度；第二，给写博管线的推理契约写一份显式的预算与停止条件文档；第三，在内容策略循环里定义假设的验证完成标准。想得清楚，也想得起来——前者靠推理契约，后者靠可核验的决策记录。
