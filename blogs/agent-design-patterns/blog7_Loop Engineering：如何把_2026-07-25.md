# blog7: Loop Engineering — 如何把 Agent 的循环工程化

> 学习笔记系列：从极客时间《Agent 设计模式之美》专栏消化核心框架，结合自身 Agent 项目实战经验，产出有个人见解的原创博客。

---

## Why：为什么「循环」值得单开一篇

在过去几个月的 Agent 开发中，我有一个反复出现的困惑：同一个模型，同样的 Prompt，有时候表现惊艳，有时候却像个新手。直到我开始系统地审视 Agent 的**循环设计**，才发现问题的根源不在模型质量，而在循环的工程化程度。

这篇的内容来自专栏的热点加餐——Loop Engineering。标题里有个关键词「工程化」，它点出了本质：Agent 开发最难的不是写 Prompt，而是设计一套**让模型在多次调用中稳定产出好结果**的循环系统。

对我来说，这篇刚好解答了我在构建 Hermes Agent 和 AI Harness 项目时反复撞到的问题：Loop 的边界在哪里？错误怎么处理？状态怎么管理？

---

## 核心框架：三个平面 + 两种 Agent

### 三个平面

Loop Engineering 提出把 Agent 循环拆成三个平面来设计，这是我今天记下的最重要框架：

| 平面 | 职责 | 数据形式 | 方向 |
|------|------|----------|------|
| 叙事平面 | 模型的思考、推理、自然语言交互 | 非结构化文本 | 发散 |
| 控制平面 | 确定性决策、信号收敛、程序分支 | 离散信号（ID、枚举、bool） | 收敛 |
| 调度平面 | 工作流状态、DAG 步骤、编排逻辑 | 状态机节点 | 协调 |

以前做传统后端，你只需要控制平面和调度平面。叙事平面是大模型时代新增的——它负责探索可能性，但不负责决策。**叙事发散，控制收敛，调度协调**，三个平面互相配合才能完成一次完整的 Agent 循环。

### 两种 Agent

另一个关键区分：**执行型 Agent** 和**内容生成型 Agent**。

内容生成型 Agent 让你写报告、做 PPT——做得好不好是主观的，10 分和 8 分的差别。执行型 Agent 是帮你下单、付款、调 API——错了就是真金白银的损失。前者可以容忍循环中的偏差，后者必须精确。

这个区分解释了为什么很多 Agent Demo 跑得很溜，一到生产环境就崩：Demo 场景基本是内容生成型，而真实业务往往是执行型。

## 对照我的项目：Hermes Agent 的循环解剖

### Hermes 的 Loop 结构

我的 Hermes Agent 本质上就是一个 Loop Engineering 的产物。它的核心循环是：

```
用户输入 → 思考（叙事平面）→ 工具调用（控制平面）→ 观察结果 → 再思考 → 响应用户
```

把这个循环映射到三个平面：

**叙事平面**：我的每一次思考过程。模型分析用户意图、规划工具调用顺序、判断任务完成度。这些都在自然语言中完成，是「发散」的部分。

**控制平面**：工具调用的参数。比如 `skill_view(name='geektime-to-blog')`——这个 name 参数必须是精确的字符串，不是「大概那个获取极客时间文章的技能」。还有 `process(action='poll', session_id='abc123')`——session_id 是从之前的 terminal 调用返回的，不能由模型「猜」一个。

**调度平面**：我的 todo 系统。当前任务列表、每个任务的状态（pending/in_progress/completed）、工具调用的顺序依赖——这些构成了我的工作流状态机。

### 最容易崩的地方：控制平面的参数漂移

实际使用中最常见的问题就是**参数漂移**。比如某次 terminal 返回了一个 session_id，下一步需要用它来 poll 结果。模型有时候会「创造」一个看起来合理的 session_id 而不是用实际返回的那个。

这就是为什么文章强调：**确定性的值必须由程序进行机械掌控，不能完全交给模型。** 我现在理解了这个原则的深层含义——不是模型不够聪明，而是叙事平面和控制平面应该各司其职。让模型管理控制平面的离散信号，就像让诗人管账本。

### Skills 系统的「复利效应」

文章提到《失控》的造物九律中有一条：**变自生变**——变化本身来自于变化，通过不断积累技能，下一轮 Loop 跑在之前的积累之上。

这正好解释了我的 Skills 系统的设计哲学。每完成一个复杂任务（5+ tool calls），我会把它沉淀为一个 skill。下一次遇到类似任务，加载 skill 就能直接复用之前的教训。比如：

- `geektime-to-blog` skill 记录了 Cookie 认证的 pitfall（不要用 `is_freelyread=true`）
- `ue5-macos-editor-debugging` skill 记录了 UE 5.8 的 `.generated.h` 问题和绕过方案
- `homelab-control-plane` skill 记录了各个本地服务的端口和启动方式

每一个 skill 都是一次 Loop 的**失败经验归档**。没有 skill 系统的话，每次都是从零开始——Loop 100 次和 Loop 1 次没区别。有了 skill，第 100 次 Loop 跑在第 99 次积累的肩膀上，这才是「复利」。

### 错误处理：失败日记的实战

我最近遇到的一个例子：在写 UE5 项目时，编译报错 `BuildId mismatch`。我手动修了一次，顺手把这个经验写进了 `unreal-engine-build-id-fix` skill。

文章里提到的「失败日记」模式就是这个意思——不是简单地记录错误日志，而是把错误**结构化存储**，让 Agent 在下一次 Loop 中能够自动回避同样的坑。我的 skill 系统现在做的是「人工版」失败日记（需要我手动创建 skill），理想的下一步是把「遇到未覆盖的错误 → 自动提案创建 skill」变成循环的一部分。

## 我的反思与补充

### Loop 的边界：什么时候该停？

文章引用了《有限与无限的游戏》的核心洞察：有限的游戏在边界内玩，无限的游戏玩的就是边界。

在我实际使用 Agent 的过程中，最难的判断是：这个任务应该给它几次尝试机会？三次？五次？一直试到成功？

我现在的经验法则：
- **执行型任务**（编译、部署、文件操作）：最多 3 次重试，第 3 次失败后必须交给人
- **探索型任务**（代码审查、架构分析）：可以给更多自由度，但需要外部验证（让用户确认关键结论）
- **内容生成型任务**（写博客、润色）：Loop 本身有价值——多轮迭代通常产出更好，但需要防止「过度润色」（润色太多轮会开始编造内容）

文章提出的那条原则很有价值：**不要让循环自己给自己打分。** 对循环本身的验证必须来自循环外部。这对应了我的实践——关键输出必须经过用户确认，不能让 Agent 自说自话地宣布「任务完成」。

### 计划活在代码里 vs 活在上下文里

文章有一个很精准的判断：「让计划活在代码里，让创意活在上下文里。」

这句话对应了我对两种 Agent 场景的区分：

- **到店吧类场景**（执行型）：工作流应该硬编码。订餐流程的 DAG 图不应该由模型在上下文中临时推理，而应该是一个确定的状态机。
- **科研探索类场景**（内容型）：流程可以更灵活，让模型在上下文中根据 Skills 和直觉去探索。

在我的项目中，`daily-blog-pipeline.sh` 就是一个「活在代码里」的计划——它是一段确定的 shell 脚本，不被模型的上下文影响。而文章消化和博客生成部分则是「活在上下文里」的创意过程。

### 我缺少的：可观测性

文章花了很大篇幅讲「玻璃罩」——可观测性。每一步 LLM 调用了什么、意图路由走到哪个值、工具调用结果是什么、循环走了几步，全部透明可见。

诚实地说，我现在的 Hermes Agent 在可观测性上做得不够。工具调用的输入输出虽然有记录，但没有一个统一的「轨迹视图」让我回溯一次完整任务的所有步骤。这是接下来要补的课。

## 总结

Loop Engineering 不是一个新概念，它是把 Agent 设计模式真正工程化的过程。核心抓手有三个：

1. **三个平面分离**：叙事发散、控制收敛、调度协调，各司其职
2. **机械状态平面**：所有确定性 ID 和参数由程序掌控，附带 Provenance（来源坐标）
3. **复利循环**：每一次 Loop 的错误和经验沉淀为可复用的资产（Skills），让第 N+1 次 Loop 跑在第 N 次的肩膀上

对我来说，最大的 takeaway 不是某个具体的设计模式，而是一个思维转变：从「怎么让模型一次答对」变成「怎么设计循环，让模型在多次尝试后必然答对」。
