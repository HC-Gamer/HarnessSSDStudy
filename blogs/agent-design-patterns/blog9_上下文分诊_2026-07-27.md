# blog9: 上下文分诊——给 Agent 装一个急诊室分诊台

上周重构 Hermes 的 skills 系统时，我遇到一个很尴尬的场面：27 个技能包，加上 MEMORY、USER PROFILE、工具定义、当前会话历史，还有用户随手贴进来的一份 3000 行日志。全部加起来，一个 session 刚开场就吃掉了小半个上下文窗口。

我当时的第一反应是"再买大一点的窗口"。但真正把 trace 拉出来看，问题根本不在窗口大小——**关键证据被挤到了中间**。用户要修的那个 bug 的错误堆栈，明明就在上下文里，模型却绕开它去分析日志里一段无关的 WARN。

黄佳老师在极客时间《Agent 设计模式之美》中把这件事命名为**上下文分诊（Context Triage）**，并给了一个我很喜欢的比喻：急诊室的分诊护士。

---

## 护士不是医生

急诊室里每个病人都想马上见医生，但护士要在门口做一次极其廉价的判断：胸痛先看、脚踝骨折等等、头疼最后。

关键在于——**护士不需要是最聪明的那个人**，她甚至不用做诊断。分诊本身就是那个快速判断。

映射到 Agent 上：分诊器不需要是模型，甚至可以是一段几十行的排序逻辑。它的唯一职责是在信息进入上下文的入口处回答三个问题：

1. 这条信息在下一步推理里有多急？
2. 它应该以原文、摘要，还是 handle 的形式出现？
3. 它离模型应该有多近？

黄佳老师特别强调了一个常见误区：**分诊不是删材料，而是控制信息和模型之间的距离。**

- **P0**：贴到模型眼前，必须看到（system prompt、安全规则、当前任务、错误堆栈）
- **P1**：进入 context，优先使用（当前文件、最近 tool 结果）
- **P2**：压缩进入，提供背景（历史对话、目录索引、日志趋势）
- **P3**：留在工具后面，按需展开（整个仓库、全量日志、知识库全文）

P2 压缩时要保留三样东西：**结论、证据、索引**。别只写"用户在排查登录问题"，要写清楚已确认什么、已排除什么、原始材料在哪个 handle 里能取回来。

---

## 我在 Hermes 里其实一直在做，只是没有名字

拿到这套框架回头看 Hermes，我发现自己早就在做分诊，只是做得不成体系：

| 上下文模块 | 我原来的做法 | 分诊后的定级 |
|-----------|-------------|-------------|
| MEMORY / USER PROFILE | 永远前置注入 | **P0**，不能被换出 |
| 当前用户消息 + 错误堆栈 | 自然带入 | **P0**，需要显式保护 |
| `<available_skills>` 索引 | 一行名称+描述 | **P2**，压缩后的目录 |
| SKILL.md 全文 | `skill_view` 按需加载 | **P3**，纯 handle |
| 用户贴进来的长日志 | 原样塞进去 ❌ | 应该降为 **P2 摘要 + P3 handle** |

最后一行就是我踩的坑。日志是"刚好被贴进来"的，不是"这一步推理需要"的，但它凭着体量优势把 P0 的错误堆栈挤到了上下文中间。

黄佳老师这句话我抄下来了：**Agent 看什么，不应该由"哪个材料刚好被检索到"决定，而应该由一套明确的分诊规则决定。**

于是我给 Hermes 的上下文装配加了一层薄薄的分诊器，核心就是"P3 永不预加载 + 错误信息强制保护"：

```python
class Priority(IntEnum):
    CRITICAL = 4     # P0: MEMORY, 安全规则, 当前消息, 错误堆栈
    IMPORTANT = 3    # P1: 当前文件, 最近 tool 结果
    SUPPORTING = 2   # P2: skills 索引, 历史摘要
    DEFERRABLE = 1   # P3: SKILL.md 全文, 长日志原文

for item in sorted(items, key=lambda x: (x.priority, x.is_error), reverse=True):
    if item.priority == Priority.DEFERRABLE:
        deferred.append(item)          # 只挂 handle，绝不展开
    elif used + item.tokens <= budget or item.is_error:
        selected.append(item)          # 错误堆栈超预算也要进
        used += item.tokens
    else:
        dropped.append(item)
```

`is_error` 那个特判是我自己加的最有价值的一行——**失败反馈永远不该静默消失**。Agent 之所以会在同一个错误上撞三次墙，很多时候不是它蠢，是第一次的报错在第二轮被裁掉了。

## 三条路线，其实是三个"谁知道什么重要"

黄佳老师拿三个工程现场做了对照，我觉得这个切片角度比结论本身更有价值：

- **Claude Code 的 CLAUDE.md 层级**——人告诉 Agent 什么重要。官方建议控制在 200 行以内，因为它 session 一开始就常驻。这里有个我以前搞错的点：`@import` 只是模块化组织，被 import 的文件启动时照样展开，**并不省 token**。真要减少常驻，得拆成 path-scoped rules 或者让 Agent 用工具去读。
- **Aider 的 RepoMap**——算法从代码结构里推断什么重要。零人工启动，面对陌生仓库很香，但它看得见结构重要性，看不见业务重要性。
- **DeerFlow 的 schema / middleware**——系统强制什么必须存在。`tenant_id`、`user_id` 这类字段不该是可有可无的 dict key，而应该是强制字段。多租户场景里，漏带身份信息不是体验问题，是安全边界问题。

成熟的系统三种全用：规则文件锁 P0，算法发现 P1/P2，schema 保证身份和权限不丢。

---

## 分诊必须可观测

这一讲最让我意外的是可观测性那一段。我原以为"加日志"就够了，但黄佳老师的三个指标确实是我没想到的：

- **分诊压力**：`budget_usage`、`dropped_count` 的 p95/p99——平均值正常不代表长尾正常
- **关键层丢失**：`p0_dropped_count` 一旦非零，那就是 bug，不是调优
- **P3 回取率**：`实际读取的 handle / 暴露的 handle`。太低说明挂了一堆没用的 handle；太高说明本该在 P2 的信息被误降到了 P3，Agent 每轮都要多绕几次工具调用

第三个指标我打算直接接到 Hermes 的 `skill_view` 上。27 个技能索引常驻，但如果某个技能连续一个月零命中，它就该从索引里下架。

---

## 总结

这一讲让我彻底换掉了一个心智模型：**上下文窗口是急诊室，不是数据库**。数据库追求完整保存，急诊室追求优先处置。

Karpathy 那个类比在这里补上了最后一块——LLM 是 CPU，上下文窗口是 RAM，文件系统是磁盘，而上下文分诊就是虚拟内存管理器：P0 是不能换出的热页，P3 handle 是很小但能把原文拉回来的页表项。所以常驻规则不能太长，因为"内核态"占多了，"用户态"就少了。
