# blog8: 感知模块导论——从"喂什么"到"怎么喂"的工程哲学

上周在给 Hermes Agent 做 skills 系统重构时，我盯着那个 `<available_skills>` 列表看了很久。415 个技能，每个有一段描述和触发条件。如果全量加载，光这个列表就要吃掉 5K+ tokens。如果不加载，模型就不知道该用什么技能。

这个问题看似是"信息检索"，但它的本质更深——它是一个**感知工程**问题。

极客时间黄佳老师在《Agent 设计模式之美》专栏的感知模块导论中，把这个问题讲透了。他引用了 Anthropic 对上下文工程的一个定义：

> 感知工程师的工作，是找出使下一次推理质量最大化的**最小高信号 token 集合**。

这句话就是我这周反复咀嚼的东西。

---

## 不是"多塞"，而是"塞对"

我最先犯的错，也是绝大多数 Agent 开发者会犯的错：**把感知等同于检索**。

用户说"帮我查退款"，系统就去搜 50 条相关文档，一股脑塞进 prompt。看起来很有道理——多给点上下文，模型自己会挑。但其实不是。

黄佳举了一个退款审核的例子。与其用 `search_docs(query="退款", top_k=50)` 把所有沾边的东西都拉进来，不如先想清楚这次推理真正需要什么：

- 订单当前状态
- 签收时间
- 用户退款历史
- 当前生效的退款规则
- 这个 SKU 的特殊限制

这五条就是"最小高信号 token 集合"。不是把所有和"退款"沾边的材料都塞进去，而是把这次判断**真正需要**的证据放进去。

我在 Hermes 的 skills 加载里完全感受过这个差异。

**错误做法**（塞满）：每次用户请求，把所有 415 个 skills 的完整 SKILL.md 都展开。每个 skill 平均 2-3K tokens，加起来接近 100 万 tokens——模型不仅慢，而且在噪音中淹死了真正相关的技能描述。

**正确做法**（塞对）：只展示一份 `<available_skills>` 索引（5K tokens），每个 skill 仅一行名称+描述。模型匹配到相关技能后，再用 `skill_view` 按需加载。这样上下文里的每一条信息都是**经过筛选的高信号 token**。

```
塞满：415 skills × 2K tokens = ~800K tokens（噪音太多）
塞对：索引 5K + 按需加载 1-3 个 skills = ~15K tokens（信号纯净）
```

---

## PRA 循环：感知决定推理的上限

专栏里贯穿始终的 PRA 循环（Perception → Reasoning → Action），我之前在双轴框架里就接触过，但这篇文章让我重新理解了 Perception 的位置。

**模型不是在真实世界里推理，它是在你喂给它的那一小块上下文里推理。**

它看不到的事实，对它来说就不存在；它看到的噪声太多，也会稀释真正重要的证据。

这解释了很多 Agent "幻觉"的根因。我之前总以为是模型能力问题，但把 trace 拉出来看，更多时候是**一开始就没有看到关键材料**。

举个例子。Hermes 有一个 `macos-computer-use` 技能，专门负责驱动 macOS 桌面——截图、点击、打字。如果用户说"帮我在 Finder 里打开那个文件夹"，而 Hermes 的上下文中没有加载这个技能，模型就会用 `terminal` 工具乱试，或者编造不存在的工具。这不是推理错了，是**感知漏了**。

黄佳给出了三个架构化的问题，我觉得可以直接用作 Agent 感知层的设计清单：

1. **什么信息有资格进入上下文？** → 相当于我设计 `<available_skills>` 列表时的筛选标准
2. **什么信息应该被压缩、排序或丢弃？** → 相当于 skill 描述只放一行而非全文展开
3. **什么信息必须在模型推理前就被结构化出来？** → 相当于 Hermes 的 MEMORY 块和 USER PROFILE 块，它们永远是"结构好的"，不是"临时检索的"

---

## 那个让我 Aha 的比喻

文章里有一个比喻我特别喜欢，因为它在我自己身上反复验证过：

> 一个中等模型读干净的 30K token，很多时候比最强模型淹在 180K 噪声里更可靠。

不是模型不够强。是你喂给它的东西太脏。

我做 UE5 项目的时候就踩过这个坑。UE 的 C++ 源码动辄几百个文件，如果你不做筛选直接把整个项目丢给模型做 code review，它反馈的往往是最长、最显眼的文件里的问题——但真正严重的 bug 常常藏在一个短小的头文件里。原因就是 Liu 等人在 TACL 2024 论文里发现的 **Lost in the Middle** 问题：模型对长上下文开头和结尾更敏感，中间位置的信息容易被忽略。

所以在 Hermes 的上下文中，我刻意把最重要的信息放在最前面：**MEMORY（个人笔记）→ USER PROFILE（用户画像）→ available_skills（技能索引）**。工具定义和其他元信息挂在后面。这个**排序本身**就是感知工程。

---

## 我在 Hermes 中的感知层设计

基于这篇文章的启发，我梳理了 Hermes 目前上下文结构中的感知层设计：

| 上下文模块 | 感知角色 | 设计原则 |
|-----------|----------|----------|
| MEMORY (95% 填充率) | 高信号、高优先级 | 固定在顶端，结构化键值对，不参与检索 |
| USER PROFILE | 中信号、稳定 | 角色定义，低频变更，同样前置 |
| available_skills | 信号索引 | 一行描述 + 按需加载，取代替换全文展开 |
| 工具定义 | 元信息 | 挂在后面，长度固定，模型用到才看 |
| 当前对话 | 即时信号 | 动态追加，自收增长 |

这里面最关键的决策是 **"索引+按需加载"**。它不是传统 RAG 里的向量检索，而是让模型自己根据用户意图从索引中挑选技能。这种机制让 tokens 花在了真正需要的地方，而不是花在"以防万一"上。

黄佳说得很对：**感知模块不是在管"检索多少条"，而是在管"信息进入上下文的资格、顺序和精度"。**

---

## 扩展思考：感知 vs 记忆

文章的另一个核心观点是感知和记忆的边界。虽然都是 Context Engineering，但方向不同：

- **感知**关注的是"这轮推理需要什么"——选择、压缩、排序**当前对话**的信息
- **记忆**关注的是"跨轮次需要保留什么"——决定哪些信息要**跨 turn 持久化**

在 Hermes 里，MEMORY 块虽然挂在上下文中（看起来像感知的范畴），但它本质是记忆层——它是跨会话持久化的，每次新会话都自动注入。而 `skill_view` 加载的技能内容就是纯感知——只存在于当前 turn，下一轮就过期。

---

## 总结

这一讲给我的最大转变，是把"感知"从一个模糊的概念变成了一个**可操作的设计清单**。每次给 Hermes 加新功能、改上下文结构，我都能拿这三个问题来过一遍：

1. 这个信息配进上下文吗？
2. 它应该被压缩、排序还是丢掉？
3. 它能不能在推理前就结构化好？

如果你也在设计 Agent 的上下文窗口，建议把这套清单贴在显示器旁边。它比"把上下文窗口塞满"优雅得多。
