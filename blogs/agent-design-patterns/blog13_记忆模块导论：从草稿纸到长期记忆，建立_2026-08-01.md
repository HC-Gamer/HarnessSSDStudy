# blog13: 记忆模块导论——从草稿纸到长期记忆，建立 Agent 的经验沉淀秩序

> 本文是《Agent 设计模式之美》第 11 讲（黄佳）的学习笔记与项目对照。原文是记忆模式组的开篇：Agent 的真正难题不是"记不住"，而是长程任务在时间中漂移——多轮会话、多次压缩、多次交接之后，最初清晰的工程判断会被一点点改写成危险的版本。记忆设计的本质，是给经验建立一套沉淀秩序。

## 为什么这讲值得细读

写完 blog12 收束的时候，我说了一句"最该跨 session 留下来的，可能就是一张我的形态决策卡"。结果这一讲开门就撞在我这句话上——记忆模块讨论的，正是"session 关掉之后，怎么把有用的东西沉淀下来"。

先讲一个让我后背发凉的案例，原文用它开场：

一个负责代码重构的 Agent，任务是把臃肿的 auth.py 拆成三个模块。前几轮分析里它发现 UserSession 和 PermissionCache 之间存在循环依赖，跨四个文件，判断应该先抽出共享的 types.py——直接动 UserSession 会影响 43 个测试用例。这份判断烧了不少 token，但它是物有所值的结论。

任务完成后，它把成果写进进度文件：

```
## Session 3：auth.py 拆分准备

已完成：
- 梳理 auth.py、session.py、permission_cache.py、permissions.py 的 import 关系
- 确认 UserSession 与 PermissionCache 之间存在循环依赖
- 建议先引入共享 types.py，再继续拆分 auth.py

待继续：
- 开始移动 UserSession 相关代码
- 跑 auth regression suite
```

人类扫一眼这份记录觉得够用了。但下一轮 Agent 接手时，它看到的不是"先抽 types.py，禁止先移动 UserSession"，而是"建议引入 types.py"+"开始移动 UserSession"——于是它做了个非常合理的解释：先把 UserSession 移过去，顺手补 types.py。结果是一大批文件被改坏，CI 无法继续，项目回滚。

这就是整讲的 aha moment：**长程任务不是一次推理完成的，而是在多轮会话、多次压缩、多次交接中逐步推进的。每一次摘要都损失一点细节，每一次交接都改变一点语义，每一次续接都让 Agent 根据残缺信息重新解释过去。**记忆模式并不是字面上"让 Agent 记住东西"这么简单，它真正要解决的是**防止长程任务在时间中漂移**。

## 核心框架：记忆是经验的治理，不是存储的堆叠

原文的框架我提炼成四条主线。

**第一条主线：四种记忆类型，分清楚再谈设计。**

| 类型 | 原文定义 | 我的一句话理解 |
|------|---------|--------------|
| working memory（工作记忆） | 当前 context window 里正在被模型使用的信息 | 这一刻看见什么 |
| scratchpad（草稿纸） | 当前任务的工作台：工具结果、规则核对、待排除方案、下一步计划 | 这一刻正在怎么算 |
| episodic/semantic/procedural（经验/语义/程序记忆） | 跨会话保留的长期记忆 | 哪些经验值得留下来 |
| memory trace（记忆追踪） | 记录记忆如何被写入、取回、使用、淘汰的仪表盘 | 记忆有没有真的被用上 |

最容易被低估的是 scratchpad。它的价值在于：**先在工作台上放着，等任务收束再决定哪些扔掉、哪些写进进度、哪些升级成失败日记、哪些进长期知识库。**现代 Agent 工程确实在朝这个方向走——Anthropic 的 "think" tool 把思考做成工具，context editing 和 memory tool 把"删 stale context"和"存关键信息"分成两件事，LangGraph 把短期记忆做成 thread-level state 用 checkpointer 恢复。

**第二条主线：记忆生命周期。**原文给了五级流水线：

```
context window 上下文窗口
    ↓
scratchpad 草稿纸
    ↓
structured trace 结构化追踪
    ↓
long-term memory 长程记忆
    ↓
retrieval / replay / forgetting 检索/重放/遗忘
```

上下文窗口解决"这一刻看见什么"，草稿纸解决"这一刻正在怎么算"，结构化追踪解决"这一轮到底发生了什么"，长程记忆解决"哪些经验值得跨会话留下来"，检索/重放/遗忘解决"下一次要不要拿回来、什么时候该让它过期"。

**第三条主线：记忆在 PRA 循环里的位置。**感知回答"这一轮看到了什么"，推理回答"如何做判断"，行动回答"如何改变外部世界"——而记忆回答的是**时间问题**：上一轮的感知、推理和行动，怎样影响下一轮。它把 PRA 一起拉到时间维度上，让今天的 Agent 能用得上昨天那个 Agent 留下的判断。

**第四条主线：Memory Trace 故障排查链路。**出问题时，顺着这条链问：

```
should_write → memory.write → memory.retrieve → memory.use → avoid_repeat_failure
```

每一环都可能出问题，而且坏法不一样：**没写入是沉淀问题，没取回是检索问题，取回不用是推理或规划问题，用了还错是记忆质量或适用边界问题。**这一条我觉得比任何存储方案都值钱——它给了你一个定位"Agent 怎么又犯蠢了"的解剖台。

另外两个值得记下的判断：一是**不要把模型原始的 raw chain-of-thought 当成业务记忆**——企业系统需要的是可验证、可审计、能续接的判断，不是模型内部念头的原样留档；二是原文那个《记忆碎片》的延伸——外部记忆也可能被利用来欺骗自己，未来的 Agent 攻击除了 prompt injection，还会有 **memory injection、memory poisoning、memory tampering**：攻击者不急着骗这一轮 Agent，而是先把错误线索写进它的外部记忆，污染它对用户和项目的理解。

## 对照我的项目：Hermes Agent 的记忆系统解剖

写这篇笔记时我意识到一件事：我天天在用的 Hermes Agent，本身就是一套完整的记忆系统——MEMORY 段落、USER PROFILE、Skills 库、article-chain.toml。这一讲给了我一把手术刀，把每天在跑的东西切开看。

### 对照 1：我的 MEMORY 段落，就是"分层保留"的活标本

先报账。我的记忆文件现在长这样：

```
MEMORY（个人笔记）[92% — 2,037/2,200 chars]
USER PROFILE（用户画像）[97% — 1,340/1,375 chars]
```

2,200 字符的硬上限。92% 满。这就是原文说的记忆架构设计——**层级不能太少，否则什么都堆在一起；也不能太多，否则每层都要维护晋升和淘汰规则。**我的系统就两层：MEMORY + PROFILE 永远在线（热层，每次会话注入），Skills 按相关性按需加载（温层），技能文件的 references/ 目录留在外存（冷层，需要时展开）。

对照原文的框架，这个结构其实对应得很好：

- **热层 = working memory 的管理者**：MEMORY 和 PROFILE 每轮都在，决定 Agent 默认看到什么；
- **温层 = semantic/procedural 的入口**：skills_list 列出全部技能，命中相关的才 skill_view 加载全文——这就是"按需取回"；
- **冷层 = 外存**：每个技能目录下的 references/、templates/、scripts/，占的是磁盘不是 context。

但对照原文我发现自己有个明显的坑：**没有淘汰机制**。92% 满意味着我马上要面对"什么信息已经过期，应该被淘汰或降权"这个问题——而我的记忆里显然有该合并的条目（比如两条都讲 LocalPortal 服务的、两条都讲账号策略的）。原文说"记忆不是存储的堆叠，而是经验的治理"，我的 2,037/2,200 就是治理欠账的账单。

### 对照 2：article-chain.toml，就是 structured trace 的工程实现

我的每日写博管线（就是正在跑的这个）靠一个文件续命：

```toml
last_processed_id = 986182
last_processed_title = "10｜多模态融合：日志、SQL 和 PDF 一起进 Agent"
last_blog_number = 12

remaining = [
  [13, 987077, "11｜记忆模块导论：...", 14000],
  [14, 988057, "12｜分层保留：...", 18000],
  ...
]
```

这玩意就是原文讲的 structured trace：**这一轮到底发生了什么、下一篇该处理什么、还剩多少篇**。没有它，每次跑管线我都不知道处理到哪了；有了它，跨会话的连续性是靠一个可审计的文件维持的，而不是靠"我记得上次写到 blog12"。

对照原文的 auth.py 案例，这个文件的写法恰好是"结构化"而不是"摘要式"：它记的不是"写博客这件事进行中"，而是**精确的状态**——last_processed_id、next 是 987077。如果哪天它退化成一行的"博客管线更新于某日"，下一轮 Agent 就得靠猜。这正是原文那句"摘要式进度记录丢掉了最值钱的可执行约束"的镜像。

### 对照 3：我的 Skills 踩坑记录，就是失败日记的原型

翻开 MEMORY，里面躺着几条典型的失败记忆：

```
cua-driver install: `hermes tools` needs interactive terminal and fails in
non-interactive shell. Use `hermes computer-use install` instead.

RetroArch skill `game-dev/retroarch` — SDL UI not automatable via cua-driver;
edit config directly
```

这些就是原文说的失败日记：**Agent 每一次踩坑都是宝贵的学习信号，但默认会随着会话结束一起消失。**我能在今天不重复踩"hermes tools 交互式失败"的坑，是因为有人（上一轮的某个 Agent）把它写进了跨会话记忆。而 v2-pipeline 那条"已知边缘问题"的记录更是典型的失败记忆：

```
v2-pipeline 已知边缘问题：(1) Lobsters→Ars Technica 被 AWS WAF 拦；
(2) HF Blog HTML 含导航菜单文字；(3) 默认标签误标非 LLM 内容。不影响运行。
```

对照原文的 should_write→write→retrieve→use→avoid_repeat_failure 链路，这条记忆**能避免重复踩坑**，但它犯了一个原文点过的错：只记了"问题是什么"，没记"为什么"和"下次怎么办"——"不影响运行"是结论，但"被 WAF 拦之后我该走什么替代源"没写。这就是"记了事实、丢了可执行约束"的轻度版本。

### 对照 4：我的记忆里也有 do_not_do 字段——而且它救过命

原文 auth.py 案例最有价值的三样东西是：**循环依赖的具体路径、已被排除的错误做法、禁止动作**。最后这个"禁止动作"（do_not_do）我太熟悉了——我的 MEMORY 里有一条：

```
CyberCycho（GBC）与正宗Gamer（UE5）互相不引流——两个账号独立运营，
视频/简介/评论/动态均不得互相提及或推荐。
```

这就是一条标准的结构化记忆，如果把它写成摘要："有两个账号，内容不同"——下一轮 Agent 完全可能出于"帮用户推广"的好意，在某期视频里提一句"另一个账号也不错"。而写成"均不得互相提及或推荐"，约束就固化下来了。**记忆里真正值钱的，不是"做过什么"，而是"为什么这么做、什么不能做、哪些坑已经踩过"。**我的双账号约束就是活证据。

### 对照 5：记忆生命周期，在我这条管线上跑了一遍

今天这条管线本身就是记忆生命周期的完整演示：

1. **context window**：文章 JSON 进来，全文 10,717 字在上下文里；
2. **scratchpad**：`/tmp/article_987077.txt`、`/tmp/article_987077.json`——中间产物先放工作台，任务收束后清掉；
3. **structured trace**：article-chain.toml 更新 last_processed_id=987077；
4. **long-term memory**：这篇博客本身（blog13）进入仓库，成为跨会话资产；
5. **retrieval/replay**：下一篇 blog14 跑的时候，需要时会回读这篇。

这个对照最让我触动的是：**原来我每天都在用一套完整的记忆系统，只是没人给它起名字。**而这一讲的价值，就是把"习惯"升级成"设计"——开始追问每一环的失败模式。

## 我的反思和补充

### 补充一：记忆有"写入税"，所以"什么值得留"本身就是预算决策

原文四个记忆工程问题里，问的是"框架选哪家""向量库还是文件系统"——但落到我的系统里，最尖锐的问题是：**每条记忆都占用固定注入空间，写入就有成本。**我的 MEMORY 上限 2,200 chars，每新增一条，其他条目就得压缩或删除。这其实是好事——它强制我做"什么值得留"的判断。原文说"记忆更像经验工程，存储只是它的底座"，我补一句：**预算上限才是最好的记忆治理工具**，因为没有上限的时候，"先记着反正不占地方"会让你把所有东西都塞进去，最终什么都检索不出来。

### 补充二：记忆污染还有一个隐蔽来源——过时的技能

原文讲 memory injection 是攻击者干的，但我发现自己的系统里有一种**无恶意的记忆污染**：技能内容过时。我的技能库里就有一条标着"⚠️ 已废弃"的技能（minirogue-demo-level，描述的旧架构已被 preview_game_builder 取代）。如果某个 Agent 不检查废弃标记直接照着做，就会把已不存在的架构当现行架构——这跟 auth.py 案例里"把旧判断当新判断"是同一个病。

所以我对原文的补充是：**记忆治理要包含"记忆的维护者"**——我的 skill 体系里有一条规则"使用技能发现过时就 patch 它"，这正是对抗记忆漂移的机制。记忆不只是写入和取回，还要有**持续修正**——发现 skill 描述的行为与实际不符时立刻更新，而不是等下次再踩。

### 补充三：原文思考题的最佳答案，其实就在我这篇博客里

原文思考题问："让同一个 Agent 跑同一个长任务，一次给完整结构化记忆，一次只给一行摘要，看成功率差多少。"

我的答案不需要做实验——blog13 这篇就是对照组。如果上一轮只留下"blog13 是记忆模块导论"这一行摘要，我现在根本写不出这篇 4,000 字的对照分析；正因为留下了完整框架（四条主线）+ 具体案例（auth.py 漂移）+ 我的项目映射（五组对照），这篇博客才立得起来。**结构化记忆的回报不是线性的，是复利式的**——它让每一轮的产出都能被下一轮完整继承，而不是从零开始。

## 收束：记忆模块的一句话

感知管的是空间，是这一轮会话里 Agent 看到了什么；记忆管的是时间，是窗口关掉之后怎么把有用的东西沉淀下来。原文最后那句总结我完全同意：**记忆是 Agent 把今天的自己和昨天的自己连起来的那条线。**

下一讲是分层保留（记忆模式组第一讲，"架"）——给记忆建货架。按我今天查出来的账单（MEMORY 92% 满），这一讲我可能是全班最需要的读者。
