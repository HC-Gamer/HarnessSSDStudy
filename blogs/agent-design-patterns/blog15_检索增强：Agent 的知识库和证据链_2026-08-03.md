# blog15: 检索增强——Agent 的知识库和证据链

> 本文是《Agent 设计模式之美》第 13 讲（黄佳）的学习笔记与项目对照。原文是记忆模式组的第二个具体模式：RAG 在 Agent 时代从"相似文本召回"升级成"可用、可信、可追溯的证据取回"——它不只是搜索框，而是 Agent 的知识供应链。

## 为什么这讲值得细读

blog14 搭完记忆货架，我给自己记了一笔："货架搭好，下一件事就是取。" 这讲开门见山讲的就是取——检索增强（RAG）。但黄佳开篇先抛了一个反直觉的问题：**RAG 为什么算记忆，不算感知？**

我第一反应也是"这不就是塞几段材料进 context 让模型看见吗"——明明参与感知。但原文一句话把我点醒：

> 感知问的是：这一次推理前，哪些材料进入 context。记忆问的是：这些长期知识怎样保存、索引、更新、过期、回滚。

RAG 的重心在前面那半段——写入侧。索引怎么建、知识源怎么登记、版本怎么管、权限怎么过滤。只看读取侧（召回、重排、引用），RAG 很容易退化成"给模型喂几段相似文本"。**能进生产的 RAG，重点在写入侧。** 这个视角转换，是整讲最值钱的部分。

## 核心框架：从"相关文档"到"可用证据"

### 机械状态 vs 业务证据：两类信息不能混

原文用一个薪酬 SaaS 场景开场：用户问"上海市场部 6 月薪资快照里的异常，哪些可以自动通过，哪些要人审"。这看起来像问答，其实混着两类完全不同的信息：

| 类型 | 内容 | 来源 | 特性 |
|------|------|------|------|
| 机械状态 | 员工 id、批次 id、考勤记录 id、奖金审批单号、金额 | 工具返回 + SessionState | 必须按位精确，程序确定性绑定，带 provenance |
| 业务证据 | 6 月薪酬规则版本、考勤扣款口径、奖金审批阈值、人审规则 | 制度文档、内部知识库 | 适合 RAG 召回，需要带版本和生效期 |

关键红线：**LLM 不能凭印象复述一个 id，更不能从 RAG 里找一个"看起来像"的 id。** 如果 RAG 召回了一段"上月奖金异常处理 FAQ"，模型把里面的 payroll_batch_id 当成本月批次 id——机械状态就被污染了。反过来，SessionState 里只有批次 id 却没有本月规则版本，Agent 又会基于缺证据的判断强行下结论。

所以执行型 Agent 里的分工是：**SessionState 提供机械真值，RAG 提供业务证据，最终决策同时绑定两者，且都带来源（provenance）**。证据和真值分属两个平面，在决策点合流。

### 朴素 RAG → 生产级 RAG：从搬运工到供应链

原文的演进叙事很清晰：

- **2020**：Patrick Lewis 等在 NeurIPS 提出 RAG——生成前先去外部库检索相关段落。
- **2023-2024**：大火、泛滥。Naive RAG = "查一次、塞进去、生成"的链式流程。
- **2025**：集体反思。Chroma 的 Context Rot 研究发现输入越长、相似度越低，模型退化越明显——"把一大堆相似材料堆进长上下文，并不会让模型更准"。ICML 2025 的 LaRA 基准得出 RAG 和长上下文没有通吃方案的结论。
- **2026**：重新定位。Agentic RAG（检索→评估→改写→再检索的循环）跨格到双轴的循环列。

朴素 RAG 像"只管把相似的货堆过来的搬运工"；**生产级 RAG 是一条带批次、带凭证、带召回能力的供应链**——关心货从哪来（source）、是不是这一批的版本（version）、能不能发到这个区域（scope）、运输途中有没有凭证可追（citation）、出了质量问题能不能召回到具体批次（trace）。

### 生产 RAG 的五道坎（为什么调 top-K 解决不了问题）

很多团队第一次做 RAG 以为问题是"召回率不够"，换 embedding、调 chunk size、把 top-K 从 5 调到 20——demo 好看，生产问题没解决。原文指出生产 RAG 的失败通常是几环叠在一起：

1. **知识源没治理**——文档过期、互相矛盾、没有 owner、一个概念多个名字。embed 进向量库后矛盾不会消失，只会变成更难排查的矛盾。
2. **切块切坏**——条款、表格、页眉页脚被硬切开，看不出属于哪一章哪一版哪一条。
3. **metadata 太薄**——只存 doc_id 和 text，缺 effective_date、product_version、region、permission_scope。
4. **召回只看语义**——企业系统里产品代码、合同编号、条款号、地区编码这些精确线索，只靠 embedding 经常漏，需要 BM25 + 稠密向量混合。
5. **答案没有引用链**——用户看到自然语言回答不知道来自哪份材料，出错后分不清是召回、重排、生成还是知识源的问题。

### 索引建设六步：让索引成为可发布的软件资产

原文给了一套拿来就能用的六步流程，这是全讲最实操的部分：

1. **知识源登记**——每份文档至少要有 doc_id、source_uri、owner、permission_scope、effective_from、effective_to、source_hash、document_status。
2. **可复现切块**——记录 parser_version、chunker_version、chunk_index、text_hash，chunk_id = hash(doc_id + parser_version + chunker_version + chunk_index + text_hash)。
3. **ingestion manifest**——记录一版索引的全部构建参数：corpus 版本、embedding 模型、hybrid 索引版本、collection 名、源文档数、chunk 数、golden_set_passed。
4. **候选索引 + 灰度发布**——先建 candidate collection，用 golden questions（业务上最容易出错、最需要稳定召回的问题）做回归，通过才进线上。**索引不是建出来就算完成，它要先证明自己能回答那些真正重要的问题。**
5. **蓝绿切换**——业务代码只访问稳定别名（如 payroll_rag_current），底层 collection 可动态切换，新索引在旁边构建验证，通过后把 alias 指过去。Milvus collection alias、LanceDB 版本化 time-travel 都是这类工具。
6. **删除、退休、备份、回滚**——被替换的规则、废止的口径不能继续参与召回，要么删除要么用 status/effective_to/permission_scope 严格过滤。每版索引都要能回答：上一版在哪、这版用了哪些源文档、召回质量下降能不能切回旧版、误入库的文档能不能定位清掉。

### 证据契约：RAG 应该返回什么

原文给"证据"下了工程定义——四件套：**source（来源）、version（版本）、scope（范围）、citation（引用）**。检索时不该只发语义查询，而是一组带业务约束的证据请求：

```python
semantic_query: "奖金增长异常 自动通过 人审 审批阈值"
filters: {
  tenant_id: "acme", region: "上海", payroll_month: "2026-06",
  employee_group: "市场部", rule_status: "active",
  permission_scope: "payroll_operator",
  required_citation: ["rule_id", "effective_from", "source_owner", "section", "index_version"]
}
```

原文给的 schema 里最惊艳的一笔是 `EvidenceRequest.mechanical_state_refs`——**记录这次检索依赖哪些机械状态，但绝不把这些机械值交给 RAG 生成**。还有 `EvidenceChunk.is_usable_on(day)`——召回到一段材料不等于它现在能用，先做过期检查。

### RetrievalTrace：给检索装一块仪表盘

最后是贯穿记忆模块的 Memory Trace 在 RAG 里的具体形态：一次错误回答可能错在四个完全不同的环节——没召回到（召回问题）、召回到了被重排压下去（重排问题）、召回到了但材料过期（知识源问题）、材料没问题模型没采纳（推理问题）。没有检索追踪，这四种错误靠日志只能靠猜。有了它，每次检索都留下：发了什么请求、用了哪版索引、召回哪些 candidate、重排留下谁、哪几条真的进了答案、没召回时的 missing_reason。

## 对照我的项目：我的系统里到处都是"玩具 RAG"

### 对照 1：Hermes 的技能系统 = 一个没有 manifest 的 RAG

读完这讲我才意识到，我每天在用的技能系统（skills）本质上就是一个 RAG——只不过它的"索引"是 SKILL.md 的 frontmatter 描述，它的"召回"是 `skill_view` 按相关性加载，它的"top-K"是每次回复前扫描可用技能列表。

对照原文的六步，我的技能库处处踩坑：

- **没有版本管理**——skill 有 version 字段但更新靠 patch，没有"这版技能基于什么知识源、何时构建"的 manifest。skill_manage(action='edit') 会覆盖旧版，但没人记录"上一版在哪"。
- **没有 golden questions 回归**——技能改坏了不会自动被发现，直到下次使用撞上。原文说"索引要能证明自己能回答那些真正重要的问题"，我的技能没有对应的回归集。
- **没有失效机制**——`minirogue-demo-level` 技能已标注废弃但仍躺在列表里参与"召回"，每次技能扫描都会看到它。这就是"旧文档还在回答问题"。
- **机械状态混入技能**——我的 MEMORY 里"夸克网盘账号 2026-08 被封禁"是时效状态，但它和长期规则（双账号互不引流）躺在同一个记忆区，没有 effective_to，没有失效检查。这不就是机械状态被放进"知识库"吗。

反过来，技能系统的**写入侧天然比玩具 RAG 强**——每篇 SKILL.md 有明确的 source_uri（skill_dir）、owner（作者）、scope（category），跟原文的知识源登记字段惊人地重合。缺的只是版本、生效期和 trace。

### 对照 2：geektime-to-blog 管线 = 一条真实的"知识供应链"

我每天跑的写博管线，恰好是原文供应链比喻的活体标本：

- **知识源登记**——`references/cookie.env` 管认证凭证，`article-chain.toml` 管文章链（这相当于索引的"候选版本清单"）。
- **可复现取数**——同一篇文章 ID，API 返回什么就是什么，parser 固定，chunk 是整篇——比原文要求的可复现切块还简单。
- **golden questions 的雏形**——每次写博客前的版权审核清单（原文 <50%、自身经验 ≥50%、标注出处）就是我的"回归测试"：这篇文章值不值得进 blog，先过一组关键检查。
- **缺 citation 链**——博客文末只标了"参考原文"，没有追到"第几讲、哪个观点来自哪段"。如果哪篇博客被指出内容有误，我没法反查到是消化时的偏差还是原文如此。这讲之后我打算在消化笔记里加一列"观点来源段落"，让 blog → 消化笔记 → 原文段落三层可追溯。

### 对照 3：双账号隔离 = 一个活生生的 permission_scope

我的 MEMORY 里有一条红线：**CyberCycho（GBC）与正宗Gamer（UE5）互相不引流，视频/简介/评论/动态均不得互相提及**。以前我只把它当"内容策略规则"，这讲之后我意识到——这就是 evidence 的 `scope` 字段！

如果把内容知识库做成 RAG，这条规则必须编码为 `permission_scope: "cyberpsycho_only"` 和 `"gamer_only"` 两个互斥 scope，检索"这期视频选题"时，属于另一个账号的知识条目必须被过滤掉。原文说"权限收紧的内部材料，不能继续躺在索引里参与召回"——我的双账号约束如果靠 Agent 自觉而不是 scope 过滤，就等于"旧文档还在回答问题"级别的隐患。模型调度（DeepSeek 编排、Sonnet 研究）也是同理：什么任务能调什么模型，是一条 Policy 级证据，不该靠上下文里"恰好有"这条记忆。

### 对照 4：LocalPortal 的机械状态 vs 业务证据

最后把原文的薪酬 SaaS 场景映射到我自己的 LocalPortal 运维：用户问"哪个服务挂了"。

- **机械状态**：端口 8088 通不通、进程活没活、tailecea 地址可达性——这些必须来自 `lsof` / `curl` 健康检查的确定性输出，绝不能让模型从某篇运维文档里"读出"端口号。
- **业务证据**：这个服务怎么启动（launchd plist 路径）、Tailscale 暴露时的 token 参数、已知的坑（AudioGuard 依赖音频设备）——这些适合放知识库，带版本和 owner。

我的现状是：机械状态靠真实命令（正确），但业务证据全部堆在 MEMORY 里没有版本。哪天 LocalPortal 更新了端口，MEMORY 不会自己过期——这就是原文说的"没有失效条件的记忆变成新判断的毒药"。

## 我的反思和补充

**1. 双轴矩阵的"跨格"启发了我对成熟度的判断。** 原文说同一个 RAG 会随工程成熟度从链式演进成循环（Naive RAG → Agentic RAG），说明双轴是描述性的、允许跨格。这改变了我对"模式"的认知——不是查表选模式，而是看我的系统现在处于链式的哪一环、缺的是哪条回路。我的写博管线目前是纯链式，如果哪天要加"先评估文章质量再决定是否消化"的反哺回路，那就是向循环演进。

**2. LLM Wiki 是对 RAG 的有力补充而非替代。** 原文提到 Karpathy 2026 年 4 月的 LLM Wiki：与其每次从原始文档重新召回重新综合，不如入库时一次性编译成结构化、可交叉引用的 markdown 页面，"编译一次、持续更新"。我的技能系统其实已经在走这条路——把经验编译成 SKILL.md，而不是每次从对话记录里检索。这验证了一个直觉：**高频复用的知识应该"编译"，低频检索的知识才用 RAG**。

**3. 我缺的是一张"证据表"。** 原文给企业 RAG 的第一件事是拿真实问题做证据表——哪些知识没有 owner、哪些过期、哪些口径冲突、哪些材料不能给当前 Agent 看。我打算给我的技能库做一次同样的审计：20 条真实任务（写博客、开 UE5 项目、诊断 Tailscale、下载夸克网盘文件）逐一问"答案依赖的知识在哪、有没有版本、失效了怎么办"。这张表做出来，技能系统的治理水平会上一整个台阶。

**4. 一个生产级补充：缺失证据的显式化。** 原文的 EvidenceRequest 有 `missing_reason` 字段，我觉得这是被低估的设计——很多 Agent 在"没召回到证据"时不会承认，而是基于现有材料强行下结论。显式的 missing_reason（"无 active 状态的奖金规则"）能让 Agent 的下一步动作从"猜"变成"请求人工提供或走默认流程"。这是把供应链的"缺货"变成可观测事件，而不是让错误悄悄传播。
