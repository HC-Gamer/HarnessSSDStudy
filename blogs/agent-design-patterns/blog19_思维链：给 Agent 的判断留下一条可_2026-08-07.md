# 思维链：给 Agent 的判断留下一条可检查的路径

我调试 Hermes 的时候经常遇到一种"薛定谔的失败"：模型输出一段分析，看起来逻辑严密、步骤分明，可我就是说不出它到底哪一步错了。重跑一遍，它换了条路径绕过去了；再问一遍，它甚至不承认上一步说过什么。直到我读到黄佳老师《Agent 设计模式之美》第 17 讲——思维链，我才意识到问题不在模型，而在我的系统从来没有"检查"过它的判断：我给的所谓"请逐步思考"，只是让模型把内心戏写出来给我看，而内心戏是没法对账的。

这篇文章，就是我把自己管线里那些"看起来在思考"的环节，重构成"每一步都能回到证据"的完整过程。

---

## 为什么要给思考留下路径？先回答一个问题

先看一个对照实验。假设任务是把一条薪资异常判断为"自动放行"还是"转人工"：

**散文式回答：**
> 综合分析了员工的工资、奖金、政策和历史记录，判断这次薪资上涨属于正常的季度奖金，可以自动通过。

**可验证命题链：**
> S1：6 月应发工资比 5 月高 18%。
> S2：增量主要来自季度奖金。
> S3：租户规则要求涨幅超过 15% 时核查审批。
> S4：季度奖金审批单存在，金额、审批人、生效月份均匹配。
> S5：S2、S3、S4 均通过验证，可以自动放行。

前一种回答你没法问"凭什么"——它把观察事实、拆解问题、核对规则、查证审批、最终判断五件事全塞进了一句话。后一种回答，每一步都是一个可以独立检查的命题：S1 去查工资快照，S2 去跑差异计算器，S4 去查审批单。哪一步错了，下游哪几步要一起作废，一目了然。

文章的核心论点就一句话：**CoT 在 Agent 里不是"写出思考过程"的提示词技巧，而是一条由可验证命题组成的工程结构。** 模型越会想，系统越要会记账。

## 核心框架：一条主路径，六个工程层，三道闸门

### 推理契约里的定位

上一讲立了推理契约（Reasoning Contract），每次任务进来回答五个问题：是否启动慎思、采用哪种拓扑、投入多少预算、由什么验证、何时停止。思维链回答其中两个：

- **采用哪种推理拓扑**——它选的是"一条主路径"：一步接一步，前一步输出成为后一步输入，不并行、不循环。适合主线清楚但中间步骤不能省的场景。
- **由什么验证**——链上的每个命题都不是模型自说自话，而是能被工具、数据库、规则引擎或人工复核独立检查的对象。

### 五步法与原子命题

文章把 CoT 步骤归成五类，我理解成一条流水线：

| 步骤 | 英文 | 干什么 | 典型命题 |
|------|------|--------|---------|
| 观察 | Observe | 把外部事实读进来 | "P 的 6 月应发比 5 月高 18%" |
| 拆解 | Decompose | 大问题拆成可验证子问题 | "增量来自哪？触发规则吗？有审批单吗？" |
| 推导 | Derive | 基于事实计算中间结果 | "增量主要来自季度奖金" |
| 验证 | Verify | 对照规则/审批/数据库核查 | "超过 15% 需要审批，且审批单匹配" |
| 决策 | Decide | 前面都通过的前提下做决定 | "本次自动放行" |

配套的纪律是"一步只表达一个可验证命题"，用三个问题检查：这一步有没有明确的立论？能不能被工具/规则/人独立检查？如果错了，下游哪些步骤受影响？三个问题答不上来，这一步就不配进入正式轨迹。

### 六层工程实现

这是全文最硬核的部分，我按自己的理解重新组织成一条落地链：

1. **Step Schema**——用 `kind / claim / depends_on / evidence_refs / validator / status` 定义"什么叫一步"。关键是 kind：不分类，模型就会把观察、解释、应用规则、做决定塞进同一个步骤；一分类型，程序就能对不同步骤施加不同约束。
2. **原子性闸门**——两类检查：静态检查（一句话里出现多个因果词/并列谓词/结论词，如"并且、同时、因此、综合来看"命中两个就判过载）+ 类型约束（Observe 必须有证据、Derive 必须有依赖和工具、Verify 必须有证据和验证器、Decide 必须有依赖和决策闸门）。
3. **验证器注册表**——"一步可验证"的隐藏条件：系统得知道谁来验证。注册表把某类谓词绑定到确定性验证器。**验证器不一定是另一个 LLM**——金额一致性交给计算器，政策生效交给规则引擎，审批权限交给权限系统，重复发放交给数据库查询。LLM 负责拆解、生成检查计划、解释结果，但不独自承担判断。
4. **依赖图（DAG）**——步骤连成有向无环图，关键在"失效传播"：S4 验证失败，S5、S6 不是"低置信度"，而是**依赖断了，必须作废**。
5. **追踪运行器**——执行结构化步骤、检查依赖、运行验证器、决定何时停止。它的职责不是替模型思考，而是当那个"刹车"。
6. **StepDraft + ClaimCompiler**——让模型先输出命题草稿（它只管"下一步想表达什么命题、属于哪类"），再由程序补充证据引用、绑定验证器、检查依赖、编译成正式节点。**LLM 的职责是拆成候选命题，程序的职责是编译成可验证节点。**

最后是三道闸门：**证据闸门**（关键判断必须绑定证据，且证据必须属于当前租户——跨租户误用证据比推理错误更危险）、**确定性验证闸门**（能用确定性程序验证的不交给模型自评）、**升级退出闸门**（证据缺失/冲突、验证器失败、关键依赖无法确认、模型两次改写同一事实，都要升级而不是硬编）。

还有一组重要区分：**供应商侧推理状态**（模型续接思考用的内部状态包，不是审计记录）与**应用侧审计轨迹**（系统自己维护的结构化记录：任务 ID、每步主张、证据引用、工具动作、验证器、最终决定、停止原因）。前者帮模型不中断，后者让系统可治理。

## 对照我的项目：思维链框架的五次对号入座

### 1. 每日写博管线 = 一条活着的 ClaimTrace

读到六层工程实现时，我后背一凉——我的极客时间写博管线每天 17:00 由 crontab 跑一遍，结构上就是一个完整的 CoT，只是我从没这样命名过它：

| 原文概念 | 我的管线实现 |
|---------|------------|
| 观察 Observe | 从 article-chain.toml 的 remaining 读第一条：blog19, 994287, 标题 |
| 证据引用 evidence_refs | cookie.env（GCESS/SERVERID/GCID），API 返回 article_content + column_had_sub=true |
| 步骤类型 kind | 加载 geektime-to-blog 技能（门禁）→ 加载 article-to-blog（引擎）→ 版权审核 → 写博客 → git 提交 |
| 验证器 validator | 版权审核清单：原文引用 < 50%、自身经验 ≥ 50%、标注出处 |
| 停止条件 stop_reason | remaining 为空自动退出；neighbors.right 为空说明专栏没新文章，管线终止 |
| 升级退出 escalate | HTTP 452 = Cookie 过期，降级到离线缓存或 Safari AppleScript |

最妙的是依赖关系：`blog19 依赖 blog18 已处理`——这体现在 last_processed_id=993323 上。如果管线中间某步失败（比如 Cookie 过期），它不是"这次博客质量低一点"，而是整个这次运行停止（依赖断了）。这正是原文说的"失效传播"。

### 2. Hermes 记忆与技能库 = 证据引用系统 + 验证器注册表

我的记忆里存的每一条，都是"命题 + 证据"的压缩结构，而不是内心戏。比如：

- "cua-driver 安装用 `hermes computer-use install`" —— 已验证命题，验证器是"interactive tty 需求"
- "permissions grant 等待 TCC 对话框，预期 timeout 124" —— 这是验证结果带观察记录
- "HUANGChengDisk 是 NTFS 只读，`cp -R src/ dest/` only，Never unmount" —— 带证据约束的操作规则

技能库本质上就是我的 ValidatorRegistry：`quark-pan-download` 技能把"夸克网盘下载"这个谓词绑定到一条确定性的 API 序列（匿名列目录 → Safari 取 Cookie → 转存 → 下载），`macos-keyboard-remap` 技能把"改键"绑定到 Karabiner 配置而不是 hidutil——因为远程注入场景下 hidutil 枚举不到键盘，这是验证过的结论。技能里的 pitfalls 段落，就是"这个命题在什么条件下会失败"的注册表条目。

### 3. 双账号隔离规则 = 证据闸门里的租户隔离

原文说"企业系统里，跨租户误用证据，是比推理错误更危险的事故"。我的系统里有一个活生生的对应：CyberCycho（GBC）与正宗 Gamer（UE5）两个账号独立运营，视频/简介/评论/动态不得互相提及；UE5 复刻 GBC 游戏作为选题时不得指向 CyberCycho。这在内容策略层面就是**租户证据隔离**——一条来自 GBC 账号的内容策略结论，不能作为 UE5 账号的选题证据。

以前我只把这条当成"品牌规矩"，现在看它是证据闸门的治理版本：推理链上每一条证据都要能回答"这条证据属于哪个租户"，回答不上来就停在草稿区。

### 4. v2-pipeline 的问题清单 = 我的原子性闸门

v2-pipeline 有三条已知边缘问题：Lobsters→Ars Technica 被 AWS WAF 拦、HF Blog HTML 含导航菜单文字、默认标签误标非 LLM 内容。我以前把它们当 bug 记在记忆里，对照"原子性闸门"的框架后，我发现它们其实是**同一类问题的三个实例：一步做了两件事**。

- 采集步骤把"抓取网页"和"通过 WAF"混在一步，AWS 拦截时整条管线就挂了——应该拆成"抓取"和"反拦截重试"两个可独立验证的命题；
- 清洗步骤把"提取正文"和"假设 HTML 干净"混在一起，导航菜单混进了正文——清洗器应该显式验证"提取结果不含导航结构"；
- 标签步骤把"打标签"和"判断内容是否 LLM 相关"耦合，误标就出现了——每个标签都应该是一个可验证命题。

这三条我过去只能靠人工清单防，现在知道该给每一步加验证器了。

### 5. UE5 编译诊断 = 我的 DECIDE 节点

用户说"用 Opus 辅助编译"时，我的处理流程是：编译 C++ → 失败则诊断（-Wshadow 警告、LiveCoding 依赖、.generated.h 缺失）→ 修复 → 重试最多 3 轮 → 启动。用思维链的语言重写：

> S1（Observe）：编译失败，错误日志含 Wshadow 警告。
> S2（Derive）：警告来自未遮蔽的局部变量声明。
> S3（Verify）：修复后重编译，警告消失。
> S4（Decide）：S3 通过，允许启动编辑器。

其中"重试最多 3 轮"就是停止条件——S4 验证失败就升级，而不是无限硬编。这个模式我在游戏项目里一直在用，现在有了正式的名字：**决策节点必须依赖已通过验证的上游节点，并经过决策闸门。**

## 我的反思：最小可用实现是什么

六层工程实现很完整，但对个人 Agent 系统，全量落地是过度设计。我的取舍是：**"一步一命题"+"三道闸门"是最小可用集，注册表和运行器可以后补。**

一个反直觉的洞察是：原文反复强调"不要信任模型自评"，但真正要防的其实不是模型撒谎，而是**模型把多个判断打包进一个步骤**——打包是幻觉的温床，因为一旦一句含四个命题的话错了，你根本不知道错的是哪个。原子性检查（哪怕只是数数因果词）是性价比最高的闸门。

第二个反思关于"该用才用"。文章结尾提醒：简单任务被硬塞推理，又慢又贵又啰嗦。我过去有个坏习惯——什么请求都默认"请逐步思考"。这就像给"现在几点"这个问题写一篇论文。推理契约的意义就在于：先判断需不需要启动慎思，再决定用哪种拓扑。思维链适合"主线清楚但中间步骤不能省"的场景；走不通就升级到并行探索或迭代假设验证，而不是硬编。

第三个补充：Provider state 和 Application trace 的区分，我完全认同但想加一句——**对独立开发者，供应商侧推理状态几乎不可控，所以应用侧审计轨迹是唯一可靠的治理抓手。** 我的系统里所有"硬规则"（双账号隔离、NTFS 只读、夸克网盘封禁）全部以外部决策记录的形式存在记忆和技能里，而不是靠模型"记得"。这就是我能做到的"让判断可检查"的全部含义。

---

## 总结

思维链教会我的不是"怎么让模型想得更清楚"，而是**怎么让系统的判断可以被对账**：一步一个可验证命题，每个命题绑定证据、依赖和验证器，由决策闸门放行，失效向下游传播。模型提出假设，程序负责验证——LLM 的职责是拆解，程序的职责是记账。

下一步我会做三件事：第一，给 v2-pipeline 的采集和清洗步骤补上显式验证器（WAF 重试、导航噪声检查）；第二，把双账号内容策略写成"租户证据隔离"的显式规则，让证据闸门有据可依；第三，为 Hermes 的核心操作（CUA 驱动、文件下载）建立真正的验证器注册表，把记忆里那些"预期 timeout 124"式的经验变成可执行验证器。
