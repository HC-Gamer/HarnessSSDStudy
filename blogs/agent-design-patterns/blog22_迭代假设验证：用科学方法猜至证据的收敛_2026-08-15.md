# 迭代假设验证：用科学方法猜至证据的收敛

昨晚 UE5 项目又编译失败了。按照我的老习惯，我立刻让模型"再试一次"——结果它在同一个地方连栽三次。三次报错字面上略有不同（一次 -Wshadow，一次 LiveCoding 依赖，一次 .generated.h 缺失），但每一次"再试"都只是把上一次的猜测换了个说法继续撞墙。我盯着终端想：我这不是在迭代，我是在重复猜测。

真正把这件事点醒我的，是黄佳老师《Agent 设计模式之美》第 20 讲「迭代假设验证」。这一讲是推理模块的收官之作——CoT 让 Agent 想得显式，复杂度路由让它想得分档，并行探索让它想得广，而迭代假设验证要解决的是最后一件事：**让 Agent 想得深，深到能查出根因为止**。

---

## 核心框架：科学方法的工程化

### 从培根到 ReAct：人类认识世界的五步进化

文章把迭代假设验证的谱系拉得很长，我理成了一条主线：

| 阶段 | 贡献者 | 思想 | Agent 对应物 |
|------|--------|------|-------------|
| 归纳 | 培根 | 推演道理先要有观察和证据 | 收集环境反馈 |
| 怀疑 | 休谟 | 再多正面例子也不能证明必然成立 | 不迷信初始高概率假设 |
| 修正 | 贝叶斯 | 新证据持续修正原有判断 | 每轮更新置信度 |
| 证伪 | 波普尔 | 主动寻找能推翻假设的反例 | 问"什么证据能证明我错了" |
| 闭环 | 维纳 | 测量偏差、调整行动 | ReAct 的 Think-Act-Observe 循环 |

这条谱系有意思的地方在于：2022 年的 ReAct 把 Thought 和 Action 交错起来，模型先想"下一步该查什么"，调工具去查，把环境返回的事实喂回下一步推理——这本质上就是把维纳的反馈闭环和波普尔的证伪原则搬进了语言模型。**我们人类花了四百年学会的事，大模型在四年里又重演了一遍。**

### 什么叫"真迭代"：三个关键词

文章给了一个我反复咀嚼的定义：迭代假设验证，是把复杂问题拆成一串可证伪的假设，通过多轮外部证据验证，把一次性猜测变成**可停机的自收敛逼近**。

关键词不是"多轮"，而是三个：

1. **可证伪**——每一轮都带着一个可以被推翻的命题进入真实环境。普通多轮对话第一轮说"可能是奖金"，第二轮说"进一步看也可能是奖金"，第三轮又补充更完整的奖金分析——表面在迭代，实际没有新证据进入，也没有任何假设被推翻，只是在旧想法上继续加厚。
2. **外部证据**——不是模型自己觉得"这个解释挺合理"，而是去真实环境里查 metric、查 log、查传感器。
3. **可停机**——循环必须有刹车，不能是 while True。这个后面单讲。

### 六步闭环：化工厂的 92℃

文章用了一个工业故障诊断案例：凌晨 3:47，聚乙烯反应釜温度从正常的 80℃ 升到 92℃。普通问答系统会说"最大可能是冷却水循环泵故障，请优先检查"。这句话看起来没错，但它不是诊断——**真正的诊断不是给出一个最像答案的答案，而是让每个假设进入验证流程**。

我按自己的理解把整个闭环拆成六步：

1. **假设生成**：生成器输出一组候选假设（H1 冷却水泵、H2 传感器漂移、H3 配方异常、H4 催化剂活性、H5 PID 被改），带概率排序——但排序只决定"先查哪个最划算"，不决定最终真相。
2. **验证执行**：每个假设被翻译成可执行检查。H1 要查冷却水流量、泵压、回水温度；H5 要查控制参数变更日志、远程登录记录、参数 diff。这一步最能区分工业 Agent 和聊天机器人——聊天机器人说"可能是冷却系统问题"，诊断 Agent 必须继续问：查哪个 metric？哪张 log？哪个时间窗口？查到什么算证伪？
3. **证据裁决**：评估器根据证据给每个假设打标——verified / falsified / partial / needs_more_evidence / human_required。H1-H3 被证伪，H4 需要实验室分析（30 分钟，停机每小时损失 45 万）进入 needs_more_evidence。
4. **人在回路**：值班工程师补充了一个关键事实——02:33 有一次远程登录修改控制参数。这个事实不是普通聊天上下文，而是高权重证据事件。
5. **上下文重置**：这条证据改变了问题的因果结构（搜索空间从"设备故障"转向"人为修改"），系统不再在旧假设树上微调权重，而是生成一份 handoff artifact（当前症状、已证伪假设、剩余假设、新证据、时间成本、目标），清空旧排序惯性和噪声，重建假设树。
6. **验证收敛**：新树把 H5' 拉到 95%，下钻参数 diff 发现 P 参数从 0.8 改到 2.5，反推与温度震荡上行吻合。恢复参数后温度回归正常——**这是最强的收敛证据：不仅解释现象，还能被干预验证。**

这套流程里最戳我的设计是**三个角色拆分**：假设生成器负责打开搜索空间，验证执行器负责拿证据，证据评估器负责剪枝裁决。为什么要拆？因为如果同一个模型既生成假设、又执行验证、又评价自己，它很容易围着初始高概率假设继续找补——H1 概率最高，它就倾向于不断在冷却水系统里找支持 H1 的解释。独立评估器的任务不是帮 H1 圆场，而是冷静地问：冷却水流量正常吗？泵压正常吗？都正常，H1 就证伪，初始概率再高也没用。

### 三种迭代范式

"提假设、验证、修正"落到工程里，常见三种变体，区别在于**检验信号从哪来**：

| 范式 | 做法 | 检验信号 | 适合场景 |
|------|------|---------|---------|
| ReAct | 边想边做，工具调用与推理交错 | 外部环境 | 探查类任务（诊断、归因、日志排查）——能拿到真实证据的优先选它 |
| Self-Refine | 先给一版答案，再自我批评修订 | 模型自己 | 写作、代码优化——但模型自己看不出的盲区，自评也照样漏 |
| Plan-then-Execute | 先生成多步计划，再逐步落地 | 执行中的偏差 | 流程清楚、步骤可预先排出的长任务 |

### 三道停机条件：迭代不能没有刹车

文章点出了一个致命风险：**迭代不一定收敛，有时候想得更多反而越改越糟**。因为模型一旦进入循环就产生"推理动量"——第一轮提出假设，第二轮不是冷静证伪，而是不自觉替它找支持，第三轮在找补基础上继续推，越走越远越自信，最后生成一大段看起来认真、实际零证据增量的解释。健康的循环每一轮都在试图推翻自己，失控的循环每一轮都在加固自己。

所以必须有三个停机条件：

1. **预算上限**：最多几轮、最多多少 token、最多多少次工具调用，到顶就停。这是硬墙，防的是失控。
2. **收敛判据**：每轮结束问"证据够不够了"。对账场景里可以非常具体——37 万缺口已经解释了多少，还剩多少无法解释。够了就停，不为"再认真一点"空转。
3. **反思哨兵**：不看绝对进度看趋势——连续两轮证据增量几乎为零，就提前拉停，防的是空转。

三道刹车分工不同：预算上限是最后的硬墙，收敛判据是循环的大脑，反思哨兵是中途急刹车。都停了还没收敛？把部分结论和未解释缺口一起交人审——人接手的已经是一个被缩小过范围的问题。

### 推理漂移与 Locked Facts

最后一块拼图是长循环特有的风险：**推理漂移**。如果第二轮已经确认"社保基数调整按 6 月生效记录归集"，到了第五轮模型又按发放日期重算社保，整张拆解表就悄悄错了。循环越长、上下文越厚，早期锁定的事实越容易被埋掉。

防漂移不能靠模型记性，要靠 trace：每一轮写清提出了什么假设、为什么、设计了什么验证、查到了什么证据、解释了多少缺口、哪些事实被锁定、为什么继续或停止。**已验证的事实一旦进入 trace 就变成 locked fact，后续每轮新假设都要和它对照，冲突就报警、回滚或人审。** 这份 trace 同时是审计依据——月底复盘时，37 万当时是怎么一块块定位出来的，翻 trace 一目了然。

## 对照我的项目

### 1. UE5 编译排障：我有假设清单，但没有反思哨兵

回到开头的编译问题。我的 UE5 编译排障流程其实已经具备迭代假设验证的骨架：编译失败 → 诊断（检查 -Wshadow 警告、LiveCoding 依赖、.generated.h 缺失）→ 修复 → 重试，最多三轮 → 启动成功。

对照文章逐条检查，我发现：

- **假设生成 ✅**：三个候选（-Wshadow / LiveCoding / .generated.h）就是 hypothesis list，编译输出就是验证信号。
- **停机条件 ⚠️ 有 max_rounds=3（预算上限），但没有反思哨兵**：三轮失败后我经常不是停，而是"再换一个说法让模型试试"——这恰恰是文章警告的推理动量，在同一个搜索空间里反复撞墙。正确的做法是三轮内连续两轮无新增解释就停，把编译日志和已试假设交给人（或换诊断路径）。
- **锁定事实 ❌ 没有**：我从不记录"第一轮已经确认 -Wshadow 是警告不是错误"这类中途锁定的事实，导致第二轮模型可能又回头怀疑它。
- **干预验证 ✅ 最强的一环**：修完代码重新编译，编译通过 + 启动成功就是收敛证据——和化工厂"恢复参数后温度回归正常"同构。

以后编译排障我会加一个明确动作：每轮把"已排除的假设"写进诊断记录，下一轮 prompt 里显式带上，防止模型重新怀疑已经证伪的方向。

### 2. 每日写博管线：整条管线就是一个迭代假设验证系统

我每天 17:00 跑一条写博管线（极客时间专栏 → 消化引擎 → 产出博客 → Git 推送）。对照这个模式一看，**这条管线本身就是个微型迭代假设验证系统**，只是我之前没意识到：

- **假设**：今天的 Cookie 凭证有效，能拉到付费文章全文。
- **验证**：POST 文章 API，检查返回状态。
- **证伪信号**：HTTP 452 = Cookie 过期；`column_had_sub=false` = 账号没订阅。两个信号都明确"这条假设被推翻了"。
- **上下文重置**：这个我有真实案例——2026-08-11 那天 Cookie 新鲜、平台正确，但持续返回 `column_had_sub=false`。我一开始在旧假设（Cookie 问题）里反复折腾，后来发现是账号问题：当前登录的微信账号没买这个专栏。正确动作不是继续调 Cookie，而是 reset：换购买专栏的账号重新扫码。这跟化工厂"02:33 远程登录"触发重建假设树完全同构——**新证据改变了问题的因果结构，就该 reset，而不是在旧上下文里继续 compaction**。
- **Locked Facts**：article-chain.toml 里记录的 `last_processed_id` 就是 locked fact——防止同一篇文章被重复消化。这个我一直在用，只是没意识到它在模式上是什么。
- **Trace**：管线日志（daily-blog-YYYY-MM-DD.log）记录了每次运行的每一步，出了错能回看"卡在哪一步、试过哪些假设（API 452？账号问题？）"。
- **停机条件**：文章链 remaining 为空时管线自动退出，绝不空转——这是天然收敛判据。

最有意思的对照是**停机条件**：写博管线天然有"专栏写完就停"的收敛判据，所以从不需要反思哨兵；但 Cookie 排障那类任务我就缺停机意识——会在"再试一次 API"上多耗好几轮，直到 452 重复出现才承认假设被证伪。文章的教训是：**452 出现一次就该触发 reset，而不是验证三次才信**。

### 3. cua-driver 排障与双轨评测：外部证据 vs 模型自评

我日常用 cua-driver 驱动 macOS 界面，权限排障也踩过迭代的坑：`permissions grant` 在非交互终端里会等 TCC 对话框等到超时（124 退出），而我不信，反复重跑——其实第一次超时就是明确证伪信号："这个假设（纯命令行能完成授权）不成立"，正确动作是 HITL：请用户去系统设置点授权，或换交互终端。

双轨评测（dual-track-eval-harness）则是另一个极端——它天然是 ReAct 式的：公网 ChatGPT 和内部生产线双轨跑同一批任务，评审量表当证据裁决。对照三范式表格，它该选 ReAct 而不是 Self-Refine 的原因一目了然：**外部证据（真实输出对比）比模型自评可靠**。模型自己说"我的输出质量没问题"不可信，双轨跑出来的差异才是证据。

### 4. 模型调度：把"继续想"换成"查证据"

我有一条调度原则：重量任务委派 Claude Code 或 Codex。对照本讲我意识到，调度不该只看任务重量，还该看**任务需要的迭代类型**：根因诊断类任务（UE5 编译失败、管线排障）应该走"假设-验证-修正"循环，每一轮都去查真实证据（编译日志、API 返回、日志文件）；而写作润色类任务才适合 Self-Refine——模型自评够了。把"让模型再想想"改成"让模型去查"，是这一讲给我最大的调度层面启发。

## 我的反思：停不下来，是我系统里最普遍的反模式

### 1. 停机条件是最稀缺的资源

对照三道停机条件查我的所有系统：预算上限我普遍有（最多三轮、超时 124、max_rounds），收敛判据部分有（管线 remaining 为空），**反思哨兵几乎全缺**。反思哨兵防的正是最隐蔽的浪费——不是无限循环，而是"预算没烧完但已经原地打转"。我那些"再试一次"的重复猜测，全部命中这个反模式。以后我会给所有重试循环加一个显式规则：**连续两轮无新增信息就停，或换路径，或交人**。

### 2. 干预验证是最高级的收敛证据

化工厂案例里，恢复参数后温度回归正常，比任何推理都强。我自己的项目里最接近的是"改完代码编译通过 + 启动成功"——但我从没把它当做一个设计目标来追求，只是碰巧达成。以后做诊断类 Agent 或排障流程时，我会把"能否构造一个干预实验验证根因"当成验收标准：**能解释现象不算完，能改回去验证才算收敛。**

### 3. 三角色拆分防的是确认偏误，而确认偏误是我最常见的 AI 使用错误

让同一个模型"换个说法再想一次"，就是文章警告的：同一个模型既猜又验，必然围着初始假设找补。UE5 编译三次失败同一处，就是找补的典型形态。以后遇到需要深度诊断的问题，我会默认拆成两个角色：一个模型提假设查证据，另一个（或独立的验证器/人）做裁决——即使后者只是"我本人看一眼编译日志"。

### 4. 一句要贴在工位上的话

文章里有句话我打算抄下来：**健康的循环，每一轮都在试图推翻自己；失控的循环，每一轮都在加固自己。** 放到我自己的日常工作里，这句话可以翻译成：每次让模型重试之前，先问一句——这一轮是带着新证据回去的，还是只是在旧想法上加厚？

推理模块四讲至此配齐：复杂度路由是分诊台，CoT 是链式诊室，并行探索是广度诊室，迭代假设验证是深度诊室。判断做出来只是"想清楚了"，下一组要讲的是行动——想清楚之后怎么稳稳地动手。我等着。
