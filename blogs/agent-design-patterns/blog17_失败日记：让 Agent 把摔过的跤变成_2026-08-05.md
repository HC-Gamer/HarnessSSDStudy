# 失败日记：让 Agent 把摔过的跤变成本事

我有一份私人的"事故台账"，藏在我的 Agent 系统里。它不记录成功，只记录摔跤。

里面有一条是这么写的：2026 年 7 月，夸克网盘 Safari 账号「Gamer」被封禁，转存/下载 API 全部返回 401 guest——原因是短时间高频转存触发了风控。旁边批注着当时最痛的那一句："需要换有效账号，下载流程见 quark-pan-download 技能。"

还有一条更早：Cookie 过期时 API 返回 HTTP 452，`curl` 不带 `-v` 时只能看到空响应体，JSON 解析直接报错——当时排查了很久才意识到是登录态失效，不是接口坏了。

写这两条的时候我根本没想过"设计模式"这个词。我只是被同一块石头绊倒过两次之后，学会在石头上刻字。

直到我读到黄佳老师《Agent 设计模式之美》第 15 讲——失败日记（Failure Journals），我才意识到：我一直在手工维护的东西，其实是一个完整的工程模式的雏形。而这篇文章，就是让我真正把这套模式做对的一次复盘。

---

## 为什么要给 Agent 记失败？先回答一个问题

上一讲的进度追踪解决的是"这一次任务怎么不跑偏"：暂停、回到上一个里程碑、修正状态、重新执行。它管的是当下。

但有一个更扎心的问题它管不了：**下一次任务，Agent 会不会在同一个坑里再摔一次？**

做 demo 的时候，我们习惯把失败藏起来。工具调用失败了？重试一次。上下文乱了？新开一个会话。中间结果错了？手工修一下。最后展示给用户的，是一条干净顺滑的成功路径。这没错——demo 的目的就是展示能力。

但坏习惯会跟着进生产。任务跑完，系统只保存最后的成功结果，失败过程随 session 一起消失。Agent 看到的是一个被打扫过的世界：它不知道哪些动作曾经失败，不知道哪种参数绑定引发过事故。下一次任务开始，它依然像个第一天上班的新人。

> **清除失败痕迹，等于清除了 Agent 唯一能用来改进的证据。**

一句话点醒我：在长循环任务里，失败本来就是循环的一部分。保留失败动作和后续观察，模型才能调整对相似动作的判断。

## 失败日记不是错误日志

最容易犯的错，是把失败日记当成 Sentry、ELK 或者异常日志的高级版。服务对象完全不同：

| 机制 | 服务谁 | 记录什么 | 是否自动影响下次任务 |
|------|--------|---------|-------------------|
| Retry | 当前执行器 | 错误码、重试次数 | 通常不会 |
| 错误日志 | 运维和工程师 | 堆栈、请求、环境 | 通常不会 |
| Postmortem | 团队 | 影响、根因、改进行动 | 靠人阅读 |
| 进度追踪 | 当前 Agent | 目标、里程碑、任务状态 | 服务当前任务恢复 |
| **失败日记** | **下一次 Agent** | **失败模式、根因、教训、召回条件** | **主动进入** |

普通错误日志回答的是："系统刚才哪里报错了？"
失败日记回答的是："以后遇到某种情形，Agent 应该提前改变什么行为？"

这个区别决定了失败日记必须完成一次**从错误事实到可行动经验的蒸馏**——不是记下发生了什么，而是记下下次该怎么做。

## 六层结构：把一次事故变成工程资产

一条失败经验不该只有一种形态。文章把它拆成六层，每一层回答一个问题：

1. **失败边界（Failure Boundary）**——这算不算值得沉淀的失败？
2. **失败分类（Failure Taxonomy）**——它属于哪种可重复的失败模式？
3. **证据包（Evidence Bundle）**——当时到底发生了什么？
4. **根因与补救（Root Cause & Repair）**——为什么错，系统该怎么改？
5. **召回触发器（Recall Trigger）**——下次什么时候该想起它？
6. **留存与审查（Retention & Review）**——谁确认它可信，该保留多久？

### 第一层：失败边界——不是只有崩溃才算失败

最危险的失败往往没有报错。四种边界里，我原来只认识第一种：

- `hard_failure`：任务无法继续——工具崩溃、权限拒绝、上下文溢出
- `gate_failure`：验证闸门没过——人数不符、金额异常、证据不足
- `semantic_failure`：**表面完成，但完成的不是原始目标**——目标漂移、口径错误
- `safety_failure`：触碰租户、权限、环境或人工审批边界

semantic_failure 尤其阴险：它生成了最终结果，看起来一切正常，但做的是错的事。我处理过的一次典型：管线在消化一篇 22K 字长文时，被文中的一个代码示例吸引，开始深挖这个示例，最后产出的博客变成了一篇"如何实现这个功能"的教程——完全忘了原任务是"消化框架+对照自身项目"。没有报错，甚至很"顺利"，但目标已经漂走了。

反过来，也不是每次抖动都值得进日记。偶发网络重试、一次无影响的格式修正，没有复发价值，留在普通日志里就行。**判断标准只有一个：它是否值得 Agent 改变下一次任务的行为。**

### 第二层：失败分类——为了召回，不是为了做百科全书

没有分类的失败日记只是一堆故事的堆砌。文章给了一张实用的分类表：tool_failure、retrieval_failure、planning_failure、goal_drift、context_contamination、mechanical_state_mismatch、boundary_leak、hitl_bypass、policy_violation、unknown。

分类是下一次召回的索引。我的事故台账里，夸克封号那条应该标 `boundary_leak`（触了平台风控边界），Cookie 452 那条标 `gate_failure`，`~` 展开到 profile home 导致 ssh 用错密钥那条标 `mechanical_state_mismatch`。**类别是召回正确经验的主要依据**——这一句话就解释了为什么要花力气分类。

### 第三层：证据包——给失败那一刻拍一张三平面快照

"Agent 用错了 payroll_group_id"不是一份完整的失败记录。你还要知道：失败发生在哪个节点？当时 Agent 以为自己在做什么？正确的参数来自哪里？哪个工具封装接受了错误值？哪条验证规则抓住了它？

这就接上了上一讲的三平面：SessionWorkspace（哪个节点失败、当前状态、重试次数）、SessionNarrative（Agent 当时的目标和判断）、SessionState（机械值从哪个工具来、属于哪个 scope、被谁消费），再加上 Raw Observation（工具输出、验证报告、错误堆栈）。

只保留原始错误，保存的是症状；把三平面和原始观察一起保留，才形成可诊断的证据包。这跟我修管线 bug 的直觉完全一致：只有 stack trace 是不够的，我得知道上下文里当时"以为自己在干什么"。

### 第四层：根因——永远不要写"模型太粗心"

失败日记里最没用的根因，是"LLM 产生了幻觉"。

因为它无法指导任何工程改进。有效的根因要落到具体动作，比如："payroll_group_id 同时存在于自然语言摘要和 SessionState，工具封装没有限制参数来源，也没有校验租户 scope，导致旧摘要中的 id 覆盖了确定性状态绑定。"

前者是甩锅，后者能直接推出一组修复：禁止从自然语言抽取机械参数、增加 scope 校验、补充回归测试。好根因的标准是——工程师和 Agent 看完都知道该从哪里动手。

### 第五层：召回触发器——写得再好，不召回等于没写

这是最容易缺的一层，也是我最痛的教训。

我的 v2-pipeline 有几个已知边缘问题：Lobsters→Ars Technica 被 AWS WAF 拦截、HF Blog HTML 含导航菜单文字、默认标签误标非 LLM 内容。这些问题**被记录过**——写在了技能文档的已知问题段落里。但它们没有 `recall_when`：没有标注服务于哪个 task_family、哪些工具、哪些参数。结果就是问题反复出现，每次都是事后发现，而不是事前预防。这就是典型的"记录不等于召回"。

文章给的结构化召回键救了我：`recall_when: task_family + tools + mechanical_keys + categories`。这样当工作流进入相关环节，就能把匹配的失败经验选择性加载——而不是在上下文里塞十条长日志。

### 第六层：留存与审查——失败日记不能变成垃圾桶

Agent 可以自动生成失败日记初稿，但不能让它写完就进召回库。四种状态：draft → needs_review → approved → archived。**只有 approved 的才能进入下一次任务。**

留存分热温冷三档：最近的失败保留完整 trace；一段时间后压缩成失败条目+证据引用；长期只保留高严重度、高复现率、真正被召回过的经验。而跨租户泄漏、人审绕过、机械状态串错这类高风险类别，不只不能自动淘汰，**还应该进入回归测试集**——一次修复过的 bug，最好的归宿不只是写进失败日记，而是变成一条永久测试。

## 三个召回点：让经验出现在该出现的地方

文章给出三个召回时机，我按价值排序：

1. **新任务启动时**——召回同 task_family 的高风险失败（最宽泛）
2. **任务规划时**——召回同场景的经验教训（中等粒度）
3. **高风险工具调用前**——按工具名和机械参数召回（最精准，**副作用就发生在那里**）

对执行型 Agent 来说，第三个时机往往最有价值。工具调用前那一刻，召回一张短短的"危险卡"，好过在上下文里塞十条长日志。真正的副作用发生在调用那一瞬间，经验必须在那一瞬间之前到达。

而且：**结构化召回键往往比纯 embedding 更可靠**。很多事故来自同一个业务动作、同一批机械参数、同一个工具入口——语义相似反而不是主线索。task_family + tool + mechanical_keys 的精确匹配，直指同类事故。

## 对照我的项目：Hermes Agent 就是一份活体失败日记

我花了很长时间才意识到：我的整个 Hermes Agent 配置体系，本质上就是失败日记的人类版实现。逐层对照：

| 框架层 | 原文概念 | 我的实现 | 差异/思考 |
|--------|---------|---------|----------|
| 失败边界 | hard/gate/semantic/safety | MEMORY 里每条"已知问题"都标注了严重度 | 只分轻重，没分类型 |
| 失败分类 | 10 类可召回分类 | 技能按领域分（devops/downloads/game-dev） | 分类维度不同：技能按任务域，失败应按模式域 |
| 证据包 | 三平面+原始观测 | 技能的 Pitfalls 章节记录失败+修复 | 只记了"怎么修"，很少记"当时以为在做什么" |
| 根因 | 落到具体动作 | 多数坑位写了修复命令 | 偶有"hermes tools 需要交互终端"这类只记症状的 |
| 召回触发 | recall_when 结构化键 | 每次任务前强制扫描技能列表（MUST load） | 这是最接近正确实现的部分！ |
| 留存审查 | draft→approved→archived | 技能创建→使用中 patch 更新→废弃（如 minirogue-demo-level） | 天然实现了状态机 |

最惊艳的发现是：**我的技能系统的召回机制，恰好就是文章说的"结构化召回键"。** 每次任务开始前，系统强制要求我扫描全部技能、凡匹配必须 `skill_view` 加载。技能名称就是 task_family，技能描述里写的"触发条件"就是 recall_when。quark-pan-download 技能为什么存在？因为夸克封号事故后，我把整个下载流程固化成技能——失败变成了可召回的资产。cua-driver 安装踩坑后，MEMORY 里写下了"用 `hermes computer-use install` 而不是 `hermes tools`"——这就是一条 approved 的经验卡。

但也有三个明显缺口：

**缺口一：没有独立的失败证据层。** 我的 MEMORY 只有 2200 字符配额，现在 95% 满。每次想记新教训都要挤掉旧的。这就是文章说的"L2 保存这次到底发生了什么，L3 保存下次要注意什么"——我的 L2 和 L3 挤在同一个地方，没有分层，导致细节必须压缩，证据常常丢失。

**缺口二：召回是全局扫描，不是定点触发。** 文章强调"高风险工具调用前"这个时机最精准。我的系统是任务启动时全局扫描——粗粒度、成本高。真正理想的是：当我要执行 `git push` 或调用某个 API 时，先召回与这个工具相关的失败经验。但我的记忆架构里没有"按 tool + mechanical_keys 召回"这个维度。

**缺口三：缺少 approved 门禁。** 我写进 MEMORY 的东西，没有经过"人审"。有的教训是我亲历的（可信），有的可能是我推断的（需复核）。文章要求只有 approved 的失败经验才能进入召回——我的系统把 draft 和 approved 混在一起了。

## 我的反思：记忆投毒是悬在失败日记上的剑

文章有一节让我后背发凉：**失败日记本身就是攻击面。**

长期记忆库 = 攻击面。未来的 Agent 攻击不只是提示词注入，还会有记忆注入、记忆投毒、记忆篡改。如果攻击者往失败日记里写一条假教训——比如伪装成"跨租户写入这步可以跳过校验"——下次召回就被污染，Agent 反而被假经验领着去犯错。

为什么比一次性提示词注入更危险？**因为它是持久的。** 恶意内容一旦写进记忆库，会在会话重启、上下文重置之后继续存活，几周后由一个语义相似的任务悄悄触发。OWASP 的 Agentic 安全倡议把记忆投毒列为十五类威胁里的头号关注点。

对策分两端：
- **写入端**：来源标记、人审、会话隔离——一条失败日记从哪来、谁审过、属于哪个租户，都要可查，不能让任意输入直接写进可召回库
- **召回端**：召回回来的历史经验是"**边界提醒**"，不是"绝对真值"。Agent 看到一条历史教训，应该把它当成一个需要再核对的提示，而不是不容置疑的指令

第二条我尤其认同——这也是为什么失败日记的第一目标不是训练数据，而是让下一次任务少犯同类错误。未经审查的失败直接拿去训练，可能把错误根因、过度概括的教训一起内化进模型。**先跑通记录、审查、召回、注入；等积累足够多经过确认的高质量条目，再考虑变成训练数据。**

## 衡量：失败日记的价值不在库容，在重复失败率

四个指标里，最核心的是**重复失败率**——已记录的失败模式又发生了多少次。

如果 mechanical_state_mismatch 一个月从十二次降到三次，这套系统在积累经验。如果日记越写越多、同类错误丝毫不降，问题出在召回点、分类、根因或教训写法上——而不是"记得不够多"。

这个指标也救了我一次误判：我曾经觉得"记录问题"就等于"解决问题"。但 v2-pipeline 那三个已知问题，记了几个月还在重复发生。原因很简单：它们被记录了，但没有召回触发器，下一次运行根本不会看到它们。**从记录到降低重复失败率，中间隔着召回这一步。**

## 黑匣子与机队

飞机失事后，调查的目的不是修好这一架，也不是责怪某个飞行员。真正的目标是读出黑匣子，把事故拆成可以命名、复现和改进的失败模式，再把改进传播到整支机队。

失败日记就是 Agent 机队的黑匣子。

错误日志服务一次维修，黑匣子服务下一次飞行。一次摔倒，应该变成所有同类任务以后都能绕开的坑。从一个 Agent 的失败，到一群 Agent 的护栏——这才是失败日记真正要做的事。

而我的行动计划也很具体：第一步，把上一讲 Verification Gate 产生的 gate_failure 和 safety_failure 自动转成失败日记草稿——证据最完整，最容易起步。第二步，给我现有的技能 Pitfalls 和 MEMORY 教训补上结构化召回键（task_family + tools + mechanical_keys）。第三步，给高风险动作（git push、API 调用、账号操作）前加定点召回。最后盯住重复失败率——让我的机队，真的学会从黑匣子里长本事。
