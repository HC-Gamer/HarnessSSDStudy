Week 3 实验心得

一、质量门禁的谎言：我建了一道只能检测"崩溃"的质量门

三个实验满分通过、零重写，我第一反应是得意。把公式代进去算完之后，我发现这道门在结构上就关不上——正常产出必然溢出上限。更难堪的是我追下去发现的东西：这个分数唯一能跌破门槛的路径，是 `json.loads` 抛异常后走 fallback，要点列表变空。也就是说，它检测的根本不是质量，是解析失败。我以为自己写了个质检员，实际上写的是个语法检查器，还给它挂了"质量"的牌子。

这让我卡在一个更难的问题上：当校验环节本身失能，谁来校验校验器？我下意识的答案是"再加一层元校验"，但这只是把问题推远一格。真正的出路不是加层数，是给校验器喂一条已知必然不及格的输入,看它响不响——用测试的思路对待度量。所以自动化管线的可信区间，不取决于我搭了几道闸门,取决于每道闸门被证伪过几次。没被证伪过的闸门，可信区间是零，不是"未知"。

二、图编排的真实成本：为一条从没走过的边，我付了三笔钱

我实际跑出来的拓扑是 START → search → analyze → quality_check → organize → END,一条直线。为了那个从未用过的 rewrite 分支，我付了三笔代价：调试复杂度——出问题时我得同时怀疑节点逻辑、状态合并和路由函数；隐式依赖——`analyze` 写分数、`quality_check` 读它写标志、`decide_route` 再读标志，这条链在图上完全看不见；以及多了一个会出错的组件，而它确实出错了。

我以前理解 YAGNI 是"别写用不上的功能，浪费工时"。这次的体会不一样：预置能力的成本不是一次性的开发成本，是**持续性的认知税**。按需加的分支，我是带着一个具体的失败案例去写的，语义必然对；为可能用到而加的分支,我是凭想象写的,而想象出来的语义没有任何东西会去检验它——它就那么带着一个错误的假设，安静地待在代码库里，还在报告里被我写成"已实现"。

三、便宜的副作用：成本归零之后，把关的动机也一起没了

不到一分钱。这个数字小到我整个实验过程一次都没打开过账单页。

我想说的不是"DeepSeek 真便宜"，是我注意到自己变了。要不要多加一个节点？加。要不要给重写留三次机会？留。三个主题都跑？跑。这些在成本高时需要掂量的决策，全退化成了"想加就加"。

我现在的判断是：成本压力有一个我以前没意识到的副产品——**它逼我为每一次调用找一个理由**。理由说不出来，调用就不该存在。而找理由的过程，顺带就会把"这次重写到底改进了什么"想清楚。这恰恰是我这次搞错的地方。成本归零，把关的动作也一起归零了，于是我加了一个自己都没想明白语义的循环节点。

所以便宜是好事，但它把稀缺资源换了个位置。省下的是钱，没省下的是我读输出、判断对错、追到根因的注意力。这次调用花的钱不到一分，我找那个覆盖 bug 花了半小时。便宜降低的是实验门槛，同时降低的是**草率的门槛**——这两件事是同一件事,只看我有没有主动把省下来的预算，重新投进验证里。这次我没有。

四、状态共享的两种哲学：我以为在选传输方式，其实在选记忆模型

V1 用文件系统：显式、可审计、可断点续跑、能手改一个中间文件再继续——这些能力我一行代码都没写，是文件系统白送的。StateGraph 用共享 dict：类型约束、无序列化损耗、节点只关心自己那几个字段，代码干净了一大截，代价是进程一退出现场就没了，还得自己防状态污染。

差别不在"传输"层面。文件传递是**外化记忆**，状态活在系统之外，进程只是路过它的临时工；共享 state 是**内化记忆**，进程死了记忆就死了。checkpointer 本质上是在用框架特性，重新实现文件系统白送的东西——而我装的 `MemorySaver` 连持久化都没有，等于一根没通电的保险丝。

我的判断：节点少于五个时，文件系统的透明度远超它那点 I/O 开销，因为这个规模下我还有能力人工审阅每一步；超过十个时，文件传递的编排负担会压垮可维护性，共享状态是唯一可行解。中间那段灰色地带需要混合——state 跑数据，同时在节点边界落盘快照，不为传递，只为留痕。可观测性的开销从来不该被记成开销。

五、方法论反思：我的结论可能只是实验设计的 artifact

这一节是我最该写、也最不想写的。

我设计这个实验是为了验证图编排的优势，但我用来支撑结论的证据是：三个主题，每个跑一轮，共三条轨迹。而这三条全是直路。我在报告里把这归因于"评分公式失效"——但这个归因本身，样本量是 3。

如果把公式修好、跑三十个主题，触发 rewrite 的比例是多少？我不知道。可能是零，说明模型在这类任务上稳定到不需要门禁，那我该拆掉这个分支；可能是三成，说明门禁有真实价值，那我该去修回边语义；也可能是九成，说明我的 prompt 才是问题所在。这三种结论指向三个完全相反的下一步，而我现在**没有任何数据能区分它们**。

更值得警惕的是：我最有把握的那几个结论——"图带来控制流显式化"、"共享状态牺牲可观测性"——都不是从这三次运行里读出来的，是我读自己的代码读出来的。它们是架构分析，不是实验发现。我把两种东西混在一份报告里，用实验的可信度给分析背了书。三次直路到底是系统性问题还是样本偏差，诚实的答案是：以我这个样本量，这个问题不成立。

六、总反思：我今天学到了什么

学到的第一件事，是我判断"这周做得怎么样"的方式一直是错的。我看的是"我造出了什么"——图跑通了、条件边生效了、循环写完了。但这些说的全是能力,而这周暴露出来的所有问题，无一例外落在另一个维度：我怎么知道它对不对。能力和可验证性是两条独立的曲线，而且我这次让它们背道而驰了——因为让系统更能干的那些手段（内存共享、自动路由、循环重试），恰恰都是让运行过程更不透明的手段。

学到的第二件事更具体：**没有被触发过的代码路径，等于不存在的代码路径**。它比"没写"更危险,因为"没写"是诚实的空白，而"写了没跑过"会让我停止思考，误以为已经有个机制在替我守着。这周我的报告里，"实现了自动重写循环"这句话技术上完全属实，实质上完全是谎言。

学到的第三件事是关于我自己的：我很擅长把系统的缺陷讲成一个漂亮的洞察。上面这五节写下来，每一节都有一个可以引用的句子——而这本身就是一个我需要警惕的倾向。真正的检验不在措辞里,在下一次运行里。所以这周唯一算数的产出不是这份心得，是那条我还没构造出来的、必然不及格的输入。
