Week 3 实验心得

一、StateGraph vs 线性：图带来的不是灵活，是"把控制流写成数据"

我一开始以为从线性管线换成 StateGraph，收获会是"更灵活"。跑完之后我觉得这个词是错的，或者至少太浅。

线性管线其实也能灵活。V1 那三个 sub-agent，我完全可以在 organizer 前面写个 if，分数低就再调一次 analyzer——十行代码的事。图结构并没有让我做到任何我原本做不到的事情。它真正改变的是**这个 if 存放在哪里**。在线性管线里，控制流藏在函数调用的嵌套关系里，你要读完整个 main 才知道数据会怎么走；在 StateGraph 里，控制流被抽出来变成了 `add_edge` 和 `add_conditional_edges` 的声明列表，节点函数只剩下"输入 state、返回 partial dict"这一件事。

这个转变的价值在我改代码的时候才显形。我想调整路由逻辑，只需要动 `decide_route` 那五行和边的声明，五个节点函数一行都不用碰。反过来，我要改分析逻辑，只动 `analyze_node`，完全不用担心影响别人怎么被调用。这是**编排和执行的解耦**——听起来像句正确的废话，但它落到手上是很具体的：我第一次感觉到"流程"是一个可以单独拿出来看、单独修改、单独讨论的东西，而不是散落在代码各处的调用顺序。

那复杂度呢？确实增加了，而且增加的地方不在我预期的位置。我以为难点会是画图，结果画图是最简单的部分。真正的复杂度来自两处：

第一是**状态的共享性本身就是耦合**。TypedDict 里那十三个字段，任何一个节点都能读、都能写。`analyze_node` 写 `quality_score`，`quality_check_node` 读它并写 `should_rewrite`，`decide_route` 读 `should_rewrite`——这条链是隐式的，图上完全看不见。图画出来的是控制流，藏起来的是数据流。V1 用文件传递的时候，谁读谁写是明摆着的：analyzer 读 `raw/*.json`，organizer 读 analyzer 的 stdout，边界物理隔离。换成共享 dict 之后，边界消失了，我得靠自律去维持它。我现在越来越怀疑，全局共享 state 在节点多起来之后会变成一个新的全局变量问题——只不过它长得像框架特性，所以没人管它叫全局变量。

第二是**循环带来了"当前是第几轮"这个新维度**。线性管线里，任何一个变量在任何时刻都只有一个值。加了回边之后，`summary` 这个字段的含义变成了"最近一次分析的结果"，它的历史被覆盖掉了。我写 `rewrite_node` 的时候脑子里想的是"带着反馈重做"，但反馈的载体是什么？是上一版的 summary，而它马上就要被这一版覆盖。我处理这件事的方式是靠 `rewrite_count` 计数——这其实是在用一个标量，去代替本该存在的一段历史。

而这个思路上的马虎，直接导致了我这次最大的一个 bug（下一节说）。所以我的结论是：图结构不是"线性的超集，用了只赚不亏"。它换来了控制流的显式化，代价是数据流的隐式化和时间维度的引入。这两样东西，线性管线是天然免疫的。

二、质量门禁 vs 无门禁：我建了一道门，然后发现门框比门低

这一节我得先承认一件事：这次实验，**质量门禁一次都没有真正生效过**。

表面上的数字是漂亮的——三个实验全部 100 分，零重写，一次通过。我第一反应甚至有点得意，觉得 prompt 写得不错。直到我回头把评分公式代进去算了一遍：摘要一百二十字，要点五条，算出来一百零四分，被 min 截成一百。门槛设在六十，而这个公式在正常产出下的**下限**大概是八十。

也就是说，这不是"质量高所以没触发重写"，这是"这道门在结构上就关不上"。我不是通过了考试，我是发的卷子里没有不及格这个选项。

这件事让我很不舒服，因为它和 Week 2 那个教训是同一个形状。上周我发现 Lobsters 那批二三十字的摘要拿到了 B 级，当时我总结的是"hook 会忠实执行我写错的标准"。这周我又干了一次，而且更彻底——上周至少评分还有分布，这周直接恒定满分。一个恒定输出的度量，它的信息量是零。我花力气搭了检测、决策、修复三个环节，唯独没有花力气去验证**检测本身有没有分辨力**。

更糟的是，因为分支从来没走过，藏在里面的 bug 就一直没暴露。我后来读代码才发现，`rewrite` 节点辛辛苦苦生成的改进版摘要，回到 `analyze` 节点之后会被**完全覆盖**——`analyze_node` 是从 `raw_content` 重新分析的，压根不读 `summary`。这条循环真正生效的只有计数器加一。换句话说，我实现的不是"带反馈的重试"，是"原地重摇三次骰子"。

这两件事叠在一起，给了我一个比"要写好评分函数"更根本的教训：**没有被触发过的代码路径，等于不存在的代码路径**。我在报告里可以写"实现了自动重写循环"，图也确实画出来了，代码也确实编译通过了，但它从未在真实运行中被执行过一次。这种"看起来有"比"明确没有"更危险——因为它会让我停止思考质量问题，误以为已经有个机制在替我守着。

所以和 V1 的无门禁比，效果如何？诚实的回答是：**这次的门禁在能力上是进步的，在效果上和无门禁没有区别**。V1 靠我人工看结果决定要不要重跑，V3 靠一个恒返回 True 的检查器决定放行。后者多了一套机制，但没多一点保障。要说唯一的收获，是我现在知道了下一步该干什么——不是把门槛从 60 提到 90，那只是换个数字继续自欺；而是先构造一条必然不及格的输入，把 rewrite 分支真正跑通一次，看看那条回边到底会发生什么。**先证明闸门能关上，再去调它关的位置。**

三、低成本的启示：便宜到无感之后，约束就换了个地方

全部实验跑完不到一分钱。这个数字小到我根本没打开过账单页面。

我想说的不是"DeepSeek 真便宜"这种废话，而是我注意到自己的行为发生了什么变化。整个实验过程里，我一次都没有因为成本而犹豫过。要不要多加一个 `search_node`？加。要不要给重写留三次机会？留。要不要三个主题都跑一遍？跑。这些决策在成本高的时候都是需要掂量的，现在全部退化成了"想加就加"。

这看起来是好事，但我意识到它有个副作用：**当一个约束消失时，我并不会自动获得对剩下那些约束的敏感度，我只会变得更随意。**

具体到这次，我给重写设上限 3，理由写的是"防止死循环"。但我现在回想，我当时脑子里几乎没有过"三次重写要多花多少钱"这个念头。如果 token 很贵，我会被迫去想清楚"这次重写值不值",从而顺带想清楚"重写到底改进了什么"——而那恰恰是我这次搞错的地方。成本压力有一个我以前没意识到的副产品：**它逼你为每一次调用找一个理由**。理由找不出来，调用就不该存在。成本归零之后，这个把关的动作也一起没了，于是我加了一个自己都没想明白语义的循环节点。

所以我现在对"便宜"的看法是：它把瓶颈从钱转移到了**注意力和验证成本**上。一次调用一厘钱，但我读一遍输出、判断它对不对、发现它有问题、追到根因——这个过程的成本一分没降。这次实验九次调用花了不到一分钱，我读代码找那个覆盖 bug 花了半小时。真正稀缺的从来不是 token。

还有一层是关于依赖的。这次我复用了 Week 2 的 `model_client.py` 和它的 CostTracker，所以三个实验共用一个全局 tracker，第三个实验报出来的成本其实是累计值不是单次值。这个细节我在写报告的时候才发现。它提醒我一件事：**成本度量做得越无感，它出错的时候越不容易被发现**。上周我抓到 USD 定价 10 倍偏差，是因为我特意去核对了；这周这个累计值的问题，如果不是我在写表格时需要拆分单次成本，可能永远不会浮出来。度量装上只是第一步，度量本身也需要被度量。

至于"本地"——严格说这次并不是本地推理，走的还是 DeepSeek 的 API。真正的本地模型是另一个成本结构：钱变成零，但延迟、显存、维护变成新的约束。我这次省下的是钱，没有省下的是每次实验四十多秒的等待。而那四十秒，在我需要反复调试 rewrite 分支的时候，才会变成真正的痛点。

四、状态共享：我以为在选传输方式，其实在选记忆模型

这一节是我这周想得最久的。

我最初把"共享 state vs 文件传递"理解成一个工程选择题：内存快、无序列化开销、有类型声明；文件慢、要 JSON 往返、没类型。按这个框架，共享 state 全面胜出，没什么好讨论的。

但跑完之后我发现这个框架漏掉了最重要的一维。文件传递有一个共享 state 完全不具备的性质：**它天然是不可变的、可追溯的、进程外的**。V1 跑完之后，`knowledge/raw/` 里躺着采集的原始数据，`knowledge/articles/` 里躺着最终产物，中间发生了什么，我事后随时可以打开来看。我没有为这个能力写过一行代码，它是文件系统白送的。

共享 state 把这个能力收走了。进程一退出，那个 dict 就没了。我得主动 dump，得主动加 checkpointer，得主动决定存哪些字段——每一样都是我要写的代码、要维护的东西。LangGraph 给了我 MemorySaver，但名字里那个 Memory 就说明了一切：它也是进程内的，进程死了一样什么都不剩。我这次装了 checkpointer，但一次中断恢复都没试过，等于装了个没通电的保险丝。

想到这里我才意识到，这两者的差别根本不在"传输"层面。文件传递是**外化记忆**——状态活在系统之外，进程只是路过它的临时工。共享 state 是**内化记忆**——状态活在进程里，进程死了记忆就死了。这是两种不同的记忆模型，而不是两种不同的传输方式。

一旦这么看，很多东西就串起来了。为什么线性管线天然可以断点续跑、可以只重跑某一步、可以让我手动改一个中间文件再继续？因为它的状态是外化的，每一步的输入都是磁盘上一个可寻址、可修改的东西。为什么 StateGraph 需要 checkpointer 这么个专门的概念？因为它把状态内化了，所以必须再造一个机制把状态外化回去。**checkpointer 本质上是在用框架特性,重新实现文件系统白送给 V1 的东西。**

这不是说共享 state 错了。它的优势是真实的：类型约束、无序列化损耗、节点只关心自己那几个字段、partial dict 自动合并——这些让代码干净了一大截，我写五个节点的过程比 V1 写三个 sub-agent 舒服太多。我的结论是这两者的取舍轴其实是：

共享 state 优化的是**开发时的表达效率**，文件传递优化的是**运行时的可观测性和可恢复性**。

前者服务于写代码的我，后者服务于半夜被叫起来查问题的我。而我这次，毫无疑问是站在写代码的我那一边做的选择——所以我拿到了干净的节点函数，也拿到了一个跑完就消失的黑盒，以及一个"藏在里面从未暴露"的覆盖 bug。这两件事是同一个选择的两面。

如果重来，我会做混合：state 里放流转中的工作数据，同时在每个节点边界把关键快照落一份盘。不为了传递，就为了留痕。这听起来是把两边的开销都担了，但我现在觉得可观测性的开销从来不该被当成开销——它是我上面那个 bug 拖了这么久才被发现的直接原因。

五、总反思：这周我造了一台更好的机器，然后没有测它

把上面四条串起来，我发现它们其实是同一件事的四个切面。

图结构让控制流显式了，但数据流隐式了；质量门禁让检测自动了，但检测本身没被检测；成本归零让实验自由了，但把关的动机也一起没了；共享状态让代码干净了，但运行现场消失了。**每一项进步都伴随一个等量的退步，而退步的那一半，全都落在"我怎么知道它对不对"这个维度上。**

这个规律太整齐了，整齐到不像巧合。我现在的理解是：Week 2 我搭的是执行能力——hooks、MCP、CI/CD，都是让系统能干更多事。Week 3 我搭的是编排能力——让系统能自己决定怎么干。而这两周，我都默认了一件事：**能力增强了，可靠性会跟着涨**。这次的结果很清楚地否定了这个假设。能力和可观测性是两条独立的曲线，而且往往此消彼长——因为让系统更能干的那些手段（内存共享、自动路由、循环重试），恰恰都是让运行过程更不透明的手段。

上周我写过一句话：Harness 里我写下的每一条规则，都是我的判断的固化。这周我想补一句：**每一条规则也都是一个未经检验的假设，直到它在真实运行中被触发过至少一次。**

零重写、满分通过，这两个数字在报告里看起来是成绩，实际上是一份"从未被测试"的证明。我做出了一个有条件路由和反馈循环的系统，但我这次跑的三轮，走的是一条和 V1 线性管线完全相同的路径——START → search → analyze → organize → END，没有分支，没有循环。我花了一周时间造了一台能拐弯的车，然后开了三趟直路，并且在报告里写"转向系统工作正常"。

下周第一件事不是加新东西，是构造一条必然不及格的输入，逼这台车拐一次弯。
