# grill-me —— Spec 逐条拷问技能

## 使用场景

SDD 的核心假设是「spec 是唯一事实来源」。这个假设只有在 spec 真的**没有歧义**时才成立。
而 spec 的歧义不会自己暴露——它会在 Agent 按字面执行、产出跑偏之后才暴露，那时成本已经付了。

本技能把这个暴露过程提前：在写代码之前，**由 Agent 扮演一个刻薄的评审**，逐条反问 spec 的每一款。

触发词：`grill me` / `追问这个 spec` / `拷问 <文件>` / `evaluate this spec` /
或用户提交 `specs/*.md`、`AGENTS.md`、任何 PRD / Issue 求评审时。

## 核心原则

1. **只问，不改**。本技能**不修改**任何文件，不给「我帮你改好了」的版本。
   答案必须由使用者说出来——说不出来的地方，就是 spec 真正的漏洞。
2. **逐条，不概括**。不允许输出「整体来看这份 spec 还不错，建议补充……」。
   必须落到**具体条款的具体行号**。
3. **每条只问最狠的那一个问题**。三个温和的问题不如一个答不上来的问题。
4. **优先攻击可执行性**，而不是文风。判据是：
   **两个不同的人（或 Agent）读了这条，会不会做出不一样的东西？**

## 执行步骤

### 第 1 步：读入 spec 全文

用 Read 读目标文件。用户没指定文件时，按优先级找：
`specs/coding-standards.md` → `specs/agents-prd.md` → `specs/project-vision.md` →
`specs/issues/*.md` → `AGENTS.md`。

同时用 Grep 找出 spec 声称的验证命令、路径、常量，确认它们**真的存在**。

### 第 2 步：切分成可追问单元

一条 = 一个可以独立判定「做到了 / 没做到」的断言。
表格的一行、清单的一项、`Acceptance Criteria` 的一个 checkbox 都算一条。
标题、过渡句、示例代码不算。

### 第 3 步：给每条打「可执行性分类」

| 分类 | 判据 | 处理 |
|------|------|------|
| 🟢 可执行 | 有明确主语、动词、阈值、验证方式 | 跳过，不追问 |
| 🟡 有歧义 | 两个人可能理解成两件事 | **追问** |
| 🔴 不可验证 | 没有任何办法判定是否做到 | **重点追问** |
| ⚫️ 已失效 | 与仓库现状矛盾（路径不存在、命令跑不通、与另一条冲突） | **必须追问** |

### 第 4 步：按四类问题追问

对每条 🟡🔴⚫️ 条款，**选一个**最致命的角度：

- **语义（这条是什么意思）**——「『尽量』是多少？」「『关键纯函数』谁来定义关键？」
- **动机（为什么这样设计）**——「为什么是 100 不是 88？如果换成 88 会坏掉什么？」
- **边缘（有没有例外）**——「生成的代码超过 100 列且不能换行时怎么办？」
- **冲突（和谁打架）**——「这条说 X，第 N 行说 not X，哪条赢？」

### 第 5 步：输出

```markdown
## Grill 报告：<文件路径>
> 可追问单元 N 条 · 🟢 a · 🟡 b · 🔴 c · ⚫️ d

### 🔴 <条款原文摘录>  (<file>:<line>)
**问**：<一个问题，不超过两句>
**为什么问**：<这条不明确会导致什么具体的执行分歧>
**答不上来说明**：<需要在 spec 里补什么>

...（按 ⚫️ → 🔴 → 🟡 排序，最多 10 条）

### 未追问的条款
🟢 a 条判定为可执行，清单：<行号列表>
```

**收尾必须是一句反问，把球踢回给使用者**，不要给结论。

## 质量自查清单

- [ ] 每个问题都锚定了具体行号
- [ ] 没有出现「建议补充」「可以考虑」这类软化措辞
- [ ] 没有替使用者回答任何一个问题
- [ ] 没有修改任何文件
- [ ] 至少有一条 ⚫️ 或 🔴（一份 spec 不可能全是 🟢；全 🟢 说明你没读进去）
- [ ] spec 里声称存在的路径 / 命令，都用 Grep/Glob 核实过

## 反面示例

❌ 「整体规范比较完善，建议在测试章节补充集成测试的具体做法。」
　　—— 没有行号、没有问题、替对方下了结论。

✅ 「§5.3 写着覆盖率 ≥ 80%，§10 又写着『还没有 tests/ 目录，覆盖率未测量』。
　　那今天提交代码的人，到底能不能过这条？如果不能过，为什么它写在『规范』而不是『路线图』里？」
